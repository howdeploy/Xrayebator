## Project

Xrayebator — automated Xray Reality VPN manager for bypassing DPI censorship in Russia. The single Bash application (`xrayebator`, ~18.8k lines) turns a VPS into a managed VPN server with an interactive terminal UI. The installer requires Bash, root/sudo, an apt-based Debian/Ubuntu-like system and systemd; the tested matrix is Debian 12/13 and Ubuntu 22.04/24.04. The **active desktop GUI** lives in `src/` (Electron + React + TypeScript) and drives the same Bash CLI over SSH. A legacy PySide6 GUI sits in `gui-legacy/` and is archival, not the active desktop app.

## Architecture

### Single-file application

All logic lives in `xrayebator`. Supporting scripts (`install.sh`, `update.sh`, `uninstall.sh`) handle lifecycle but are not part of the runtime. The repository is a single runtime source file, but a deployed VPS is not literally one file: `xrayebator` generates additional root-owned runtime artifacts from heredocs — `/usr/local/bin/subhttp.sh` (the subscription/geo HTTP handler, which sources `xrayebator` in source-mode), systemd units (`xrayebator-sub.service`, `xrayebator-expire.service/.timer`, `xrayebator-traffic.service/.timer`, `xrayebator-monitor.service/.timer`, backend units) and nginx vhosts. Never edit those on the server — change `xrayebator` and regenerate.

### Production paths

- `/usr/local/etc/xray/config.json` — Xray configuration (inbounds, routing, DNS)
- `/usr/local/etc/xray/profiles/*.json` — per-user profile metadata
- `/usr/local/etc/xray/.private_key`, `.public_key` — Reality keys (generated once at install, never regenerated)
- `/usr/local/etc/xray/backups/` — timestamped config backups (created by `backup_config()`)
- `/usr/local/bin/xrayebator` — symlink to the script
- `/etc/systemd/system/xray.service.d/security.conf` — drop-in: `User=xray`, `CAP_NET_BIND_SERVICE`

### Critical concept: Inbound vs Profile

An **inbound** is a port-level config block in `config.json` (tag: `inbound-443`). A **profile** is a user-facing JSON file with UUID/transport/SNI metadata. Multiple profiles can share one inbound (same port). SNI and port are **inbound-level** — changing either can affect ALL profiles on that port. Fingerprint is **client-side per profile/route** and changing it does not edit the inbound or other routes. The function `update_all_profiles_on_port()` keeps profile JSONs in sync after inbound-level changes.

### Transport compatibility and flow

All TCP sub-types (`tcp`, `tcp-utls`, `tcp-xudp`, `tcp-mux`) map to network `"tcp"` and can coexist on one inbound (same port). But they require different `flow` values per client:

| Transport | network | flow |
|-----------|---------|------|
| tcp, tcp-utls, tcp-xudp | tcp | `xtls-rprx-vision` |
| tcp-mux | tcp | `""` (empty) |
| grpc | grpc | `""` (empty) |
| xhttp | xhttp | `""` (empty) |

Flow is determined by transport type in `add_inbound()`, NOT copied from existing clients. Mixing Vision and non-Vision transports on one port is valid — each client gets its own flow.

### XHTTP special case

XHTTP transport stores SNI in TWO places: `realitySettings.serverNames` AND `xhttpSettings.host`. Both MUST match. The function `update_transport_settings_for_sni()` handles this.

### Firewall port management

- `open_firewall_port(port, proto)` — idempotent, validates port, checks UFW
- `close_firewall_port(port, proto)` — only closes if port unused by any Xray inbound AND not in default ports list (22, 80, 443, 8443, 2053, etc.)

### Safe restart and backup

- `safe_restart_xray("/exact/backup/path")` — validates config with `xray run -test -format json` before `systemctl restart`; on failure it attempts rollback from the exact operation backup. Always use it for runtime mutations owned by `xrayebator`, and pass the operation's exact backup path.
- `backup_config("migration_name")` — creates timestamped config backups in `/usr/local/etc/xray/backups/`. **Call before any config mutation** in migration functions.
- `fix_xray_permissions()` — restores the root-owned manager-state boundary after writes. The service account reads required files; it does not own manager scripts or migration markers. Generated metadata and lifecycle rollback paths may have narrower exceptions.
- `install.sh` and `update.sh` have separate validation/restart/rollback paths; do not assume every lifecycle restart calls `safe_restart_xray()`.

### Migration system

Marker files in `/usr/local/etc/xray/` (e.g. `.xhttp_migrated`, `.config_optimized`). Migrations run once on first `main_menu()` launch after upgrade — and `quickstart` runs the same critical set (`test-quickstart-migration-parity.sh` keeps them in sync). Pattern for new migrations:
```bash
if [[ ! -f "/usr/local/etc/xray/.my_migration_marker" ]]; then
  backup_path=""
  backup_config "my_migration" backup_path
  # ... safe_jq_write calls ...
  fix_xray_permissions
  touch "/usr/local/etc/xray/.my_migration_marker"
  safe_restart_xray "$backup_path"
fi
```

### Security model

Xray runs as non-root user `xray` with `CAP_NET_BIND_SERVICE` via systemd drop-in file. The `install.sh` creates the user and sets file ownership. The `safe_jq_write()` function preserves `644` permissions; `fix_xray_permissions()` restores ownership after writes.

### Add-on services (legacy deprecated behavior)

- **AdGuard Home** — Removed from the interactive menu before the 3.0 line. If `/opt/AdGuardHome/AdGuardHome` is detected during `xrayebator update`, update.sh force-uninstalls it through `_adguard_force_uninstall_if_present` after rolling Xray DNS back to DoH Local (`https+local://1.1.1.1/dns-query`). `uninstall_adguard_home()` remains in `xrayebator` for manual emergency use.

## Coding Patterns

**Language**: Bash. Core runtime dependencies include `jq`, `curl`, `ufw`, `systemctl`, `openssl`, `uuidgen`, `qrencode`, `ip`, `ss`, `getent`, `flock`, `timeout`, `base64`, `awk`, `sed`, `stat`, `find`, `cmp`, `readlink`, `sha256sum`, `unzip`, `install`, `sysctl` and `hostname`; nginx, certbot, socat and snap are required by particular subscription/self-steal modes. Validation CI additionally installs `ripgrep`.

**Variables**: Always quote (`"$var"`), always `local` in functions.

**Safe JSON writes** — use `safe_jq_write()` for ALL jq modifications to config.json and profile files. It validates output is non-empty before `mv`, preventing data loss on jq errors:
```bash
safe_jq_write --arg uuid "$uuid" --argjson port "$port" \
  '(.inbounds[] | select(.port == $port) | .settings.clients) += [{"id": $uuid}]' \
  "$CONFIG_FILE"
```
Do NOT use raw `jq ... > temp && mv temp file` — always go through `safe_jq_write`. Note: `safe_jq_write` is only available inside `xrayebator`; `install.sh` and `update.sh` use inline jq followed by a `[[ -s ... ]]` non-empty check before `mv`.

**jq argument passing**: Use `--argjson` for numeric ports, `--arg` for strings. Never interpolate variables into jq expressions.

**Error handling in create_profile**: `add_inbound()` can fail (transport conflict, SNI conflict rejection). `create_profile()` checks the return code and deletes the profile file on failure. Always check `add_inbound` return.

**Client counting**: When checking if an inbound has remaining clients (e.g. before deleting the entire inbound), count via `config.json` clients array, NOT by counting profile files on disk. Profile files can be out of sync.

**Menu pattern**: `while true; do show_ascii; ... read choice; case $choice in ... 0) return ;; esac; done`

**Colors**: `RED` (errors), `GREEN` (success), `YELLOW` (warnings/prompts), `BLUE` (menu borders), `CYAN` (info/options), `MAGENTA` (section headers), `NC` (reset).

**Port validation**: `[[ ! "$port" =~ ^[0-9]+$ ]] || [[ $port -lt 1 ]] || [[ $port -gt 65535 ]]`

**Restart discipline**: Never use bare `systemctl restart xray`. Always use `safe_restart_xray()` which validates config first and auto-rolls back on failure.

**Freedom outbound**: When modifying freedom outbound settings, use jq path assignment (not object merge) to avoid clobbering existing `fragment` anti-DPI settings.

## CLI commands

Apart from the interactive menu (`sudo xrayebator`), the script exposes subcommands used by the GUI and by automation. They are dispatched at the very bottom of `xrayebator` (the `case "${1:-}" in ... esac` block guarded by `XRAYEBATOR_SOURCED`):

- `xrayebator update` — update only the Xray-core binary; `xrayebator update <branch>` self-updates the manager from the canonical raw branch, pins that branch in `/usr/local/etc/xray/.current_branch` (the GUI updater reads this file), then updates Xray-core.
- `xrayebator-update [branch]` — separate full `update.sh` lifecycle workflow; without a branch it displays `.current_branch` and opens interactive branch selection.
- `xrayebator quickstart --email <email>` — UI CLI used by the desktop app: runs the broad setup/migration path, provisions the subscription endpoint, creates a standard **schema-v3 multi-route** HAPP profile (7 routes including `xhttp-legacy`), and prints JSON with `subscription_url`. The implementation currently tolerates migration failures in this non-interactive path; verify the resulting profile and services after deployment. Email mode is explicit: `quickstart --without-email` runs the same path but registers Certbot/ACME with `--register-unsafely-without-email` (no renewal notices, no email-based account recovery; never substitute a fake address). The GUI passes exactly one of the two forms, plus the optional blocks: `--pq` when the operator enabled the PQ toggle, and `--dns01-domain/--dns01-provider/--dns01-token|--dns01-aws-*` when the DNS-01 fallback was filled in. `--pq` is opt-in and default OFF (a client without ML-KEM cannot connect to a PQ port); it adds a PQ route to the managed profile, and a server without ML-KEM keys still deploys — the JSON then reports `pq_route:false`. The PQ block MUST stay after `_happ_ensure_default_multiroute_profile` returns: it was once nested inside that function's failure branch, which made `--pq` dead code while the static test kept passing (order is now guarded by `validation/test-dns01-certbot.sh`). If Let's Encrypt cannot validate the IP over http-01 (hoster filters port 80 — "Connection reset by peer" from validation hosts) **and** DNS-01 was requested, quickstart tries DNS-01 first (see below); only if that also fails does it degrade to `http_tls`: markers switch to that mode, the subscription is published over HTTP from the loopback handler, a self-signed cert is generated for future backends, and the result JSON carries `degraded:true`, `tls_mode:"http_tls"` and `certbot_reason`; the renew timer is NOT installed in this mode, and rerunning quickstart after port 80 is unblocked issues the LE certificate and restores ip_tls (guarded by `validation/test-quickstart-tls-fallback.sh`).
- `xrayebator inspect --json` — read-only install probe for the GUI "connect existing server" import: reports manager/Xray/profiles/subscription markers as one JSON object on stdout (diagnostics to stderr only). It must not migrate, install, restart, open firewall or write anything; `validation/test-quickstart-email-and-inspect.sh` guards these invariants statically. Since the multi-protocol stage it also carries a secrets-free `backends` summary (`{<type>: {installed, version, port}}`) read from the backend registry only when the file already exists — inspect never creates it.
- `xrayebator happ-setup` — reduced existing-install HAPP path; ensures the subscription service and a usable multi-route profile, verifies a real public TLS endpoint when subscription markers are missing, and prints JSON with `subscription_url`. It does not have the same migration breadth as quickstart.
- `xrayebator probe-test` — probe-test candidate SNIs from `sni_list.txt` and print reachability scores.
- `xrayebator profiles` — print all profiles as a flat JSON array (used by the GUI "Server settings" page); each entry carries `expire` (epoch seconds, `0` = unlimited), server-local `expire_date` (`YYYY-MM-DD`) for display, `expire_disabled`, and since the multi-protocol stage the additive `backends` object (per-profile hysteria2/awg grants — operator-level credentials, same trust level as the already-exposed `sub_token`). `expire_supported` is present (`true`) only on servers with expiry enforcement; its absence means the server predates the feature and the GUI must not offer expiry. Since the subscription-formats stage the entry also carries `subscription_url_clash` and `subscription_url_singbox` (same token with `?target=` prefilled) — additive, so older GUIs keep working.
- `xrayebator dns01-setup --domain sub.example.com --provider cloudflare|route53 [--token T | --aws-access-key-id K --aws-secret-access-key S] [--email E|--without-email] [--port P] [--staging]` / `dns01-status` / `dns01-test` — DNS-01 subscription TLS (menu `6` → `8`). Proves domain ownership with a TXT record instead of http-01, so **inbound :80 is not required** — this is the documented escape from `http_tls` degradation on hosters that filter port 80. Installs `python3-certbot-dns-cloudflare` / `python3-certbot-dns-route53`, writes provider credentials `0600` root (`DNS01_CLOUDFLARE_INI` = `/etc/letsencrypt/xrayebator-dns01-cloudflare.ini`, `DNS01_AWS_INI` = `…-aws.ini` handed to certbot via `AWS_SHARED_CREDENTIALS_FILE`), runs `_dns01_certbot_args_pure` (`certonly --cert-name D -d D --dns-<provider> … --non-interactive --agree-tos --deploy-hook "systemctl reload nginx" [-m E | --register-unsafely-without-email]`), renders `_dns01_nginx_vhost_pure` (one TLS server; deliberately no `listen 80` and no ACME location), registers the cert in `.certbot_owned` via `_certbot_register`, opens only the subscription port with `limit_firewall_port`, writes markers through `_subscription_write_markers … "domain_tls"`, and records the provider in `DNS01_MARKER_FILE` (`/usr/local/etc/xray/.dns01_provider`). `dns01_setup_command` prints only JSON on stdout (progress goes to stderr via the `exec 3>&1` trick) and validates domain/provider/credentials **before** any system call, so failed calls write nothing. Renewal is the standard `certbot.timer` plus the deploy hook — no custom timer. `xrayebator repair-dns01 --domain D --provider P […]` reuses `_dns01_install` to convert a **degraded** `http_tls` subscription to DNS-01 (idempotent: an `ip_tls`/`domain_tls` subscription returns `{"ok":true,"skipped":true}`), and `quickstart --dns01-*` runs the same install as the second fallback — after http-01 failed, before `http_tls` — skipping the IP nginx template and the IP markers exactly like `repair-dns01` does. `uninstall.sh` removes both credential files. Guarded by `validation/test-dns01-certbot.sh` (pure parts functionally, wiring statically — live DNS APIs are not available in CI).
  - **ACME staging contour and `dns01-test`.** Let's Encrypt allows 5 certificates per exact set of identifiers per 168 h (refilled one per 34 h) and 5 failed validations per identifier per hour, so a debugging session can block the next meaningful issuance — a live server ended up with `retry after 2026-10-19 02:02:28 UTC`. `--staging` on `dns01-setup` / `repair-dns01` / `quickstart` (or `XRAYEBATOR_ACME_STAGING=1`) resolves through `_acme_staging_on` and adds certbot `--test-cert` (staging allows 30000 orders per week); the run warns loudly, reports `staging:true` in JSON and writes `/usr/local/etc/xray/.acme_staging` (`_acme_staging_mark`). `dns01-status` decides the contour from the **certificate on disk** (issuer containing `(STAGING)`) and uses the mark only as a fallback when the certificate is unreadable — renewals run through `certbot renew` outside xrayebator and would leave the mark stale (verified live: the mark survived while `live/<ip>` already held the production certificate, and the status/GUI claimed the subscription was untrusted). The production path now always names the endpoint (`--server "$ACME_PRODUCTION_URL"`): without it a repeat issuance under the same `--cert-name` would inherit the server from its renewal configuration and stay in staging. `xrayebator dns01-test --domain D --provider cloudflare|route53 [--token T | --aws-*] [--email E|--without-email]` is the verification-only issuance: staging, its own lineage (`DNS01_TEST_CERT_NAME` = `xrayebator-dns01-test-<epoch>`, so a repeat run cannot "pass" on an existing certificate), no deploy hook, no vhost/markers/firewall/subscription side effects, JSON with `issuer`, `not_after`, `txt_name` (`_acme-challenge.<domain>`), `cleaned`, and on failure the parsed `_certbot_failure_reason`. Pure seams: `_dns01_test_certbot_args_pure`, `_dns01_resolve_port` (one port rule for both DNS-01 paths: explicit `--port` → current subscription port → `443`; before that the GUI button silently moved a `:8443` subscription to `:443`), `_dns01_renewal_has_hook` (certbot writes `--deploy-hook` as `renew_hook`, so grepping `deploy-hook` reported `deploy_hook:false` on every real domain — `dns01-status` now accepts both spellings). `_dns01_install_plugin` (shared by the real and the test path) picks the certbot that actually reports the provider plugin via `_dns01_pick_certbot`: apt certbot 1.x carries the `dns-*` plugins while snap certbot 5.x carries `--ip-address`, so a `PATH` with `/snap/bin` first would otherwise fail with `unrecognized arguments: --dns-cloudflare`. `_apt_certbot_timer_disable` turns off the distribution `certbot.timer` only when the shortlived IP lineage is renewed by a snap binary (apt certbot cannot handle that lineage and failed twice a day); `_dns01_install` re-enables it for a domain certificate, and `uninstall.sh` restores it if the flag `/usr/local/etc/xray/.apt_certbot_timer_disabled` is present.
- `xrayebator profile-pq --name NAME [--transport tcp|tcp-utls|tcp-xudp|tcp-mux|grpc|xhttp]` — add a post-quantum VLESS Encryption route (`mlkem768x25519plus`). VLESS `decryption` is **inbound-level**, so `_pq_add_route_for_profile` picks a free port via `build_transport_defaults` (that function only *chooses* a port — it creates nothing), creates the inbound with `add_inbound` under a `backup_config` snapshot, switches that inbound's `.settings.decryption` to the shared key from `.vless_decryption` via `safe_jq_write`, appends a `<transport>-pq` route with `pq_enabled: true` + `schema_version: 2`, and then calls `safe_restart_xray` (rolling the route and the port back if Xray refuses the config) — without the inbound and the restart the route is dead: the port never listens, UFW never opens it and the generated `link` is empty (that was a live defect on Ubuntu 22.04, hidden by a test that pre-created the inbound). The jq variable for the route label is `$lbl`, **not** `$label`: on jq 1.6 (Ubuntu 22.04, Debian 12) the object pair `label: $label` is a syntax error because `label` is a keyword, while jq 1.7 accepts it — `validation/test-jq-keyword-compat.sh` guards that whole class. `_generate_vless_url_pure` therefore derives `encryption=` from `pq_enabled` for **any** transport (a PQ route without `.vless_encryption` returns 1); `_profile_route_matches_live_inbound` requires `decryption != none` for PQ routes and `decryption == none` for plain ones on every transport; the v2ray/base64 body drops all PQ routes because a client without ML-KEM cannot use them (the HAPP body keeps them — HAPP has ML-KEM); the Clash/sing-box renderers skip them with a reason. `profile_pq_command` validates name/transport, refuses duplicates and missing keys, prints only JSON (progress on stderr) and includes the generated link. `profiles` carries the additive `pq_routes` counter (routes with `pq_enabled`), because top-level `.pq_enabled` mirrors only the first route — the GUI's PQ chip reads `pq_routes`. A profile from `profile-create` is in the **single-route shape** (transport/port/SNI only at top level, no `routes`), so `_pq_add_route_for_profile` first expands that shape into `routes` (keeping port/transport/SNI/fingerprint and the `grpc`/`xhttp` metadata) and only then appends `<transport>-pq`; appending straight onto an empty `routes` silently dropped the base route from the subscription, from `channel-test` and from `profile-delete` (live 2026-10-20). `profile-pq` likewise refuses a transport that is already post-quantum in the single-route shape — the normal case for `--transport xhttp`, where `profile-create` already sets top-level `pq_enabled` and the inbound `decryption`. Guarded by `validation/test-pq-routes.sh`.
- Subscription formats (Clash/mihomo + sing-box): the `subhttp.sh` handler serves four bodies from one token — HAPP, base64 v2ray, Clash/mihomo YAML, sing-box JSON — selected by `?target=clash|mihomo|singbox|sing-box|v2ray|base64|happ` first and then by `User-Agent` (`mihomo`/`clash`/`stash`/`flclash`; `sing-box`/`sfa`/`sfi`/`sfm`/`nekobox`/`hiddify`/`karing`; `v2rayNG`/`v2rayN`), defaulting to the HAPP body so already-issued links keep working. All formats render from the same normalized link set: `_subscription_links_json` parses the `vless://` URLs produced by `_generate_vless_urls_for_profile` (plus the hysteria2 link) into records carrying per-client support flags, `_subscription_render_clash_pure` emits YAML (proxies/proxy-groups/rules, `reality-opts`, `flow`, `client-fingerprint`, `packet-encoding: xudp`, `grpc-opts`, hysteria2) and `_subscription_render_singbox_pure` emits JSON (outbounds, `tls.reality` + `utls`, `transport.type=grpc`, selector/urltest/direct, `route.final`). Routes a client cannot use are skipped with a reason instead of being emitted broken — PQ/VLESS Encryption (neither client supports it), xhttp in sing-box (no such transport), xhttp in Clash without `?xhttp=1` (mihomo ≥ 1.19; an unknown `network` makes mihomo refuse the whole config) — and `subscription-userinfo` is now sent for every format. The handler is regenerated on existing servers by migration `subhttp_formats_2026` (registered in `main_menu`, `quickstart` and `happ-setup`). The body branch for base64 is selected by the resolved `sub_format`, **not** by the UA-derived `universal_sub` flag: `?target=v2ray|base64` used to fall into the HAPP branch and return a plaintext HAPP body (byte-identical, PQ routes included) because only the User-Agent set that flag (live defect 2026-10-20). The HAPP body also no longer drops an xhttp route just because the profile has a legacy `encryption=none` xhttp route: that rule predated HAPP's ML-KEM support and silently removed `xhttp-pq` (7 links in the body vs 8 working routes). Handler changes reach existing servers only through a migration — `subhttp_v2ray_pq_2026` (registered in `main_menu`, `quickstart` and `happ-setup`). Guarded by `validation/test-subscription-formats.sh`.
- `xrayebator profile-create --name NAME [--transport T] [--port P] [--count N] [--expire DATE]` — create 1..N profiles non-interactively (names `name`, `name-2`, ...). `--expire` accepts `YYYY-MM-DD[ HH:MM]`, epoch seconds or 13-digit milliseconds; date-only expiry is inclusive through `23:59:59` in server-local time, while an explicit time uses server-local time as given. Dates/times with leading-zero fields such as `09` are parsed as decimal, not octal. A past expiry is rejected. Emits `{"ok":true,"names":[...],"errors":[...]}`; `ok` stays `true` even when some profiles already exist (they land in `errors`). The GUI additionally pre-checks a name collision before issuing the create call (deletion is per-profile: unique names keep it precise, and the deleted profile's backend keys are revoked immediately — see the lifecycle bullets above).
- `xrayebator profile-delete --name NAME` — delete a profile, emits `{"ok":true,"name":"..."}` (stdout carries only the JSON — the `backup_config` status line is silenced to stderr like the other helpers). Inbound/firewall cleanup happens automatically, and the deleted profile's backend grants are revoked in the same command: the AWG peer is regenerated out of `awg0.conf`, the Hysteria password out of `server.yaml` — no orphaned credentials; the name is immediately free for reuse. The port set comes from `_profile_ports_json`, the **union** of top-level `.port` and every `.routes[].port`: choosing "routes if non-empty, else .port" hid the base port of a mixed profile, so the inbound stayed in `config.json` with the deleted profile's uuid and kept listening (live 2026-10-20). The interactive delete and `expire` share that helper.
- `xrayebator profile-revoke --name NAME [--full]` — reissue the subscription `sub_token`; `--full` also rotates the uuid in every inbound of the profile, so already-downloaded configs stop connecting. Transaction order matters: config + `safe_restart_xray` first, then the profile JSON, and a failed profile write rolls the config back from the transaction backup.
- `xrayebator profile-expire --name NAME --expire DATE|epoch|none` — set/extend/clear a profile expiry (`.expire` epoch seconds); date-only expiry is inclusive through `23:59:59` in server-local time; an explicit time is also interpreted in server-local time. Applied immediately (an expired profile loses its client, an extension restores it).
- `xrayebator expire-check` — batch enforcement of every due expiry; idempotent (no changes ⇒ no Xray restart), driven by `xrayebator-expire.timer` every 10 minutes. Disabling keeps the inbounds alive (a fresh inbound would change the shortId and kill issued URLs) and snapshots clients into `.expire_clients` for restoration.
- `xrayebator profile-limit --name NAME --limit 500MB|1.5GB|2TB|<bytes>|none [--reset]` — set/clear a per-profile traffic limit and/or reset its counter (units case-insensitive, decimals allowed; `none` = unlimited, stored as `0` in `.traffic.limit`). `xrayebator traffic-check` is the batch workhorse behind `xrayebator-traffic.timer` (every 5 minutes): it queries the Stats API (`xray api statsquery` against the loopback `api` inbound, port read from `config.json`, `10085` by default), accumulates per-profile deltas into `.traffic.used` using `.traffic.last` as the watermark (an Xray restart therefore does not lose already-counted bytes), then enforces the limit. The client `email` equals the profile name — that identity is what makes the Stats API per-profile, and every profile-creation path writes the profile JSON before `add_inbound`. Accounting covers Xray routes only: Hysteria 2 and AmneziaWG traffic is not counted by `traffic-check` (their own backends would have to report it), so a profile with a hysteria2/awg grant can exceed its limit when the client uses that backend. Enforcement removes the client from the inbound and snapshots it into `.traffic_clients` (transport flow preserved), setting `.traffic_disabled`; the subscription then answers `410 Gone` and `subscription-userinfo` reports real `download`/`total`. Raising or clearing the limit restores the same client. `expire` and traffic limits are cross-guarded: `_expire_enable_profile` returns `rc=3` (flag cleared, client NOT restored) while a traffic limit still blocks the profile, and the traffic path mirrors this for expiry. Backend regen filters `.traffic_disabled == false` as well. Per-user counters exist in Xray **only** when `policy.levels."0".statsUserUplink/Downlink` are `true` (`app/dispatcher` gates `user>>>EMAIL>>>traffic>>>uplink` on `Stats.UserUplink`/`UserDownlink`; `policy.system.statsInbound*` is inbound-level statistics) — `install.sh` writes them, `traffic_stats_2026` backfills them, and `traffic_user_stats_2026` repairs servers whose earlier migration marker would block that backfill. `profiles` exposes `traffic_used`/`traffic_limit`/`traffic_disabled`/`traffic_supported`, where `traffic_supported` is `true` only when the api inbound and those level flags are actually present (same "hide what the server cannot do" contract as `expire_supported`; the GUI hides limit management when it is `false`). Migrations `traffic_stats_2026`, `traffic_user_stats_2026` (repair), `traffic_timer_2026` and `subhttp_traffic_2026` are registered in `main_menu`, `quickstart` and `happ-setup`. Guarded by `validation/test-traffic-limit-cli.sh`.
- `xrayebator fp-change --name NAME [--route R] --fp FINGERPRINT` — change the fingerprint for a profile (client-side, no Xray restart), emits JSON.
- `xrayebator sni-change --name NAME [--route R] --sni SNI` — change the SNI for a profile; updates all profiles on the same port (`update_all_profiles_on_port()`), emits JSON.
- `xrayebator sni-list` — print the SNI candidates from `sni_list.txt` grouped by category, emits JSON (used by the GUI SNI dialog). The file lives in `$DATA_DIR` (`/usr/local/etc/xray/data/sni_list.txt`); its first uncommented line is the default for new profiles. `_default_sni_for_transport` does **not** trust that line blindly any more: it verifies reachability from the server with the shared pure seam `_sni_tls_output_ok_pure`, which requires a **completed TLS 1.3 handshake with a verified certificate** — not the bare `Verify return code: 0`, because openssl prints that even when the handshake failed ("no peer certificate available"), which made TLS 1.2-only hosts and hosts that answer `sslv3 alert handshake failure` look reachable and gave fresh profiles dead routes (live 2026-10-20: 4 of 6 new PQ routes returned http 000 with such SNIs and 200 after switching to `www.cloudflare.com` on the same port). `_monitor_sni_reachable` and `probe-test` use the same seam. Candidate order is the per-transport default, then at most `SNI_REACH_HEAD_MAX` (4) lines of `sni_list.txt`, then the global fallbacks (`www.cloudflare.com`, `api-maps.yandex.ru`, `www.google.com`), then the rest of the list — the list is `ru_whitelist`-first, so from a foreign VPS every dead entry costs a full timeout and an unbounded walk made profile creation crawl. Criterion details that cost a live debugging round: match the version as the substring `TLSv1\.3`, not as the `Protocol  : TLSv1.3` line — OpenSSL 3.0 on Ubuntu 22.04 prints no such line under `-tls1_3` (only `New, TLSv1.3, Cipher is …`), and requiring the line rejected live `www.cloudflare.com`/`www.google.com`/`api-maps.yandex.ru`, after which the walk crawled into the list tail (67–84 s per profile); a failed handshake also shows `Cipher is (NONE)`. A successful probe is repeated once and both attempts must pass, and a host must also answer HTTP (`curl` code ≠ 000, the status itself irrelevant) because a dest that completes TLS and then tarpits still breaks the client handshake — `www.wildberries.ru` passed TLS in 1.7 s with `000` from curl and its route hung 10 s. The repeat catches hosts that answer only intermittently (`splitter.wb.ru` failed with alert 40 in one measurement and passed in another) — Reality on such a dest drops the client handshake. Budget per attempt is `SNI_REACH_TIMEOUT` (default 3 s — a working TLS 1.3 handshake answers in 40–250 ms, a dead host burns the whole budget), and `probe_sni` uses the same value so `probe-test` cannot claim `TLS OK` for a host that selection rejects. One probe per SNI is cached (`_SNI_REACH_CACHE`) and the old behaviour stands when nothing is reachable. Use `idx=$((idx + 1))`, never `((idx++))`, in loops here: the latter returns 1 for index 0 and kills callers running under `set -e`. Reason: Reality serves the client a certificate fetched from the SNI's real site, so an unreachable `dest` hangs the handshake while the config stays valid — on a live deployment the default `www.ozon.ru` was unreachable and 5 of 7 routes of a fresh deployment were dead (`xrayebator channel-test` proved it). Guarded by `validation/test-sni-reachability.sh`.
- `xrayebator channel-test [--name NAME] [--url URL] [--timeout S] [--transport T]` — verify that the profile's channels actually work: for every route it starts a local Xray client (SOCKS5 on a loopback port) from the subscription link and pushes a real request through it, printing JSON (`ok`, `working`, `checked`, per route `label`/`transport`/`port`/`pq`/`ok`/`http`/`ms`/`client_log_tail`; progress goes to stderr). No Let's Encrypt involvement — Reality and VLESS Encryption are self-contained, so it works on an `http_tls` subscription and before any certificate exists, and it covers PQ routes. Helpers are the seams: `_channel_client_config_pure` (pure client config from a link record), `_channel_free_socks_port`, `_channel_wait_socks`, `_channel_probe`. Do **not** touch fd 3 inside those helpers: `channel_test_command` owns it (`exec 3>&1 … exec 1>&3`) and a stray `exec 3>&-` sent the final JSON to stderr (found live). Guarded by `validation/test-channel-test-cli.sh` (network run itself is live-only: the CI suite cannot start Xray clients against real inbounds). Do not read a single measurement as a verdict: the **first** run right after an Xray restart pays connection warm-up and can report ~5 s per route, while the second run of the same profile reports ~150 ms (measured on a live server: plain 5179 → 149 → 151 ms, PQ 241 → 232 → 229 ms). Run it twice before calling a channel slow — and note that PQ is not automatically faster or slower: after warm-up plain Reality over the same `www.cloudflare.com` SNI was ~150 ms and the PQ route ~230 ms, the difference being one ML-KEM encapsulation.
- `xrayebator port-change --name NAME [--route R] --port PORT|random` — change the port for a profile; updates the inbound, firewall, subscription and all profiles on the port, emits JSON (reconnect is required).
- `xrayebator bypass list|add --domain D|remove --domain D|reset|bundle [--group a,b,c]` — manage bypass routing groups (JSON). Server-side only: it exists for cascade deployments, where the catch-all points at the upstream; without a cascade the built-in catch-all already sends everything direct.
- `xrayebator backend-start --type hysteria2|awg` — bring an *installed* backend whose unit is not active back up (after a reboot, or a manual down). The only mutation is `systemctl start` (plus the kernel module for AWG), and it prints JSON, reporting `already:true` when the unit was running. The desktop GUI exposes it as the **Start** button next to the red "Not running" state — that is why `backend-status` reports `installed` and `state` separately: an installed backend can be dead, and the GUI must not paint that green.
- `xrayebator backend-status` — print the multi-protocol backend registry status as JSON (`{"ok":true,"backends":{...}}`). Backend state lives in the neutral root `/usr/local/etc/xrayebator/` (`backends.json` registry 644 root — no secrets, readable by the `xray` service account; `backends/<type>/` runtime state with secrets in 750/640); `/usr/local/etc/xray/*` stays Xray-only. Slice 1 of the multi-protocol stage (2026-10) ships the registry with no backends; `hysteria2` and `awg` entries appear as those backends land. `_backend_apply_profile_lifecycle <name> <created|deleted|revoked|expired|restored>` is the single lifecycle choke point for backend grants; per-profile backend credentials live in the profile's additive `.backends` object, so the profile JSON remains the single source of truth for revoke/expire. Guarded by `validation/test-backend-registry.sh` (sources the script in source-mode with an overridden `BACKENDS_ROOT`).
- `xrayebator hysteria2-install [--port P] [--grant-all]` / `hysteria2-uninstall` / `hysteria2-status` / `hysteria2-grant --name N` / `hysteria2-subbody --on|--off` / `hysteria2-link --name N` — Hysteria 2 UDP backend (multi-protocol slices 2–3, menu item 11). Install downloads the binary from `HyNetworks/hysteria` releases (tag format `app/vX.Y.Z`, sha256 from the API `digest` field), creates the dedicated `hysteria` system user, writes its own `hysteria-server.service` (CAP_NET_BIND_SERVICE, `Restart=on-failure`), QUIC sysctl buffers, and `/usr/local/etc/xrayebator/backends/hysteria/server.yaml`. TLS is adaptive: a subscription Let's Encrypt cert is copied into the backend dir with a certbot renewal deploy-hook, otherwise a self-signed cert is generated (clients then use `insecure=1`). CLI commands print only JSON on stdout; exit code `2` from the workhorse means "already installed / not installed" and the wrapper reports `already: true`.
- Hysteria 2 grants (slice 3): per-profile credentials live in the profile's `.backends.hysteria2` object (`username` = profile name, `password` = 32 hex chars) — the profile JSON is the single source of truth; `server.yaml` is always **regenerated** from profiles by `_hysteria2_regen_config` (compact users map, filter `.expire_disabled == false`, so `expired`/`restored` events are just a regen) and applied via `_hysteria2_apply_config` (restart with rollback). `_backend_apply_profile_lifecycle` is wired after the Xray part of `create_profile` / `_profile_cli_create_one` (created — **no-op**: backend keys are NOT auto-issued on creation, the operator picks the protocol explicitly via the GUI create flow or explicit grant CLI — otherwise every new profile would receive keys from ALL installed backends), `profile_delete_command` (deleted), `profile_revoke_command` (revoked → password rotation), and `_expire_disable_profile`/`_expire_enable_profile` (expired/restored). Install asks to grant all existing profiles interactively; the CLI is non-interactive by default and opt-in via `--grant-all`. The pure builder `_hysteria2_profile_link_pure` produces `hysteria2://user:pass@host:port/?sni=…&insecure=0|1#name`; the subhttp handler appends it to BOTH the generic (v2rayNG) and the HAPP subscription bodies, gated by the registry `sub_body` flag (kill-switch without service restart). Migration `subhttp_hysteria2_2026` regenerates the handler on existing servers and is registered in BOTH `main_menu` and `quickstart` (parity test). The registry file is 644 root (no secrets) so the `xray` service account can read it from subhttp; secrets live in the 750 backend dirs. HAPP-body acceptance with a hysteria2 line is verified in the live spike, not CI.
- `xrayebator awg-install [--grant-all]` / `awg-uninstall` / `awg-status` / `awg-grant --name N` / `awg-conf --name N` / `awg-31 --on|--off` — AmneziaWG 2.0/3.1 system-VPN backend (multi-protocol slices 4–5 + 3.1 stage, menu items 12/13). Kernel module via DKMS per the AmneziaWG README: primary path is the `amnezia/ppa` PPA (`apt install amneziawg`), fallback is a manual source build (kernels ≥5.6 need the FULL `linux-source` tree linked as the module's `kernel` symlink — headers alone are not enough). The backend is registered in the registry only after `modprobe amneziawg` + `lsmod` confirm the module and `awg show awg0` confirms the interface, and verifies the module through `_awg_verify_module`, which also writes `/etc/modules-load.d/xrayebator-awg.conf` (`AWG_MODULES_LOAD_FILE`) so systemd loads the module at boot: without that file a reboot left `awg-quick@awg0` failed with `Error: Unknown device type`, `awg0` absent and the tunnel dead while the registry still said `installed` (live defect, fixed by the idempotent `awg_module_2026` migration plus `_awg_ensure_runtime`, which `awg-install` re-runs on an existing installation; `awg-uninstall` removes the file, its own `rm -f "$AWG_MODULES_LOAD_FILE"`). The install path judges the PPA branch by `_awg_module_for_kernel` (a `.ko` for the *running* kernel, root override `AWG_MODULES_ROOT` for tests), never by `command -v awg`: a stale binary from an earlier manual build made the branch report success after a kernel upgrade, so the source-build fallback never ran and the module was never rebuilt for the new kernel (live defect: 5.15.0-177 → -198). When `modprobe` still fails, `_awg_verify_module` prints the kernels the module exists for (`_awg_module_kernels`). Server state: `backends/awg/server-params.json` (0600, keys/port/iface/junk) and `awg0.conf` (0600). AWG 3.1 is implemented and ON by default: the generator emits `S1`–`S4` (≥ 12), `HeaderProtectionKey` (random, shared with every client conf) and `RandomTrailers = on` — the `awg` parser (kernel UAPI) accepts booleans as `on`/`off`, NOT `true`/`false`; `DisableCookies` is available via `awg-31 --disable-cookies` (local flag, off by default). `awg-31` toggles the format with an explicit operator warning that every issued client `.conf` must be re-downloaded (clients need AmneziaVPN ≥ 5.0.1.5) and regenerates the interface with rollback; `_awg_ensure_31_params` upgrades legacy (pre-3.1) server params in place. Junk params mirror the Amnezia defaults — the dialect the official AmneziaVPN apps (phone and desktop) apply reliably; their go-tunnel applies custom junk incompletely: Jc=5, Jmin=10, Jmax=50, H1–H4=1..4 (WG magic), S1/S2 random 12..150, S3/S4 random 12..64, all unique with S1+56≠S2. The desktop GUI additionally delivers keys in the app-native `vpn://` shape (`amnezia-awg2` container, server-side junk fields, `protocol_version`; see shared/awg.ts `buildAwgVpnConfig`) — a raw `.conf` pasted into AmneziaVPN does not reach its tunnel intact. `ip_forward` is set via `/etc/sysctl.d/99-xrayebator-awg.conf`. Uninstall tears down the interface and files but leaves the packages/module in the system (documented in output).
- AWG peers (slice 5): per-profile peer credentials live in the profile's `.backends.awg` object (`client_private_key`, `client_public_key`, `preshared_key`, `address` `10.8.1.x`, `created`) — profile JSON is the single source of truth; `awg0.conf` `[Peer]` sections are **regenerated** from profiles (`_awg_regen_config`, filter `.expire_disabled == false`, so expired/restored events are just a regen) and applied via `_awg_apply_config` (interface restart with rollback; the restart briefly drops the tunnel for all peers — accepted for stage 1, grants/revokes are rare). Address allocation picks the first free `.2..254` honoring addresses already issued to profiles. The lifecycle choke point dispatches to `_awg_on_profile_event` automatically for installed backends — deleted/revoked/expired/restored need no extra wiring in profile flows (created is a no-op: no auto-grant, keys are issued only by explicit `awg-grant`; the `deleted` case regenerates unconditionally because the caller removes the profile file BEFORE the lifecycle call). Client config (`_awg_client_conf_pure`) carries the client keypair, the server pubkey/endpoint, junk params copied from the server, `AllowedIPs = 0.0.0.0/0, ::/0` (full tunnel) and `PersistentKeepalive = 25`; `awg-conf --name N` returns it as JSON `{ok, name, conf}` for the GUI, the menu prints it with an optional QR. Peer events: revoked = keypair+PSK rotation with the address kept (old client configs stop connecting). Package installation itself (network + DKMS build) and a real client connection are verified in the live spike, not CI.

- `xrayebator alerts-setup --token T --chat-id C` / `alerts-status` / `alerts-test` / `alerts-enable|alerts-disable` / `monitor-check [--force-sni]` — Telegram alerting for server monitoring (menu item 14). It is **terminal-only by design**: the desktop GUI has no alerts surface at all (no IPC channel, no settings card, no i18n keys), so the bot token has exactly one entry point. Config is `alerts.json` (0600 root: bot token + chat_id + bot username) in the neutral root `/usr/local/etc/xrayebator/` — deliberately NOT in `/usr/local/etc/xray/`, which stays Xray-only; the token is never printed, including by `alerts-status`. `alerts-setup` validates the token with `getMe` and delivers a test message to the chat BEFORE writing the config, so an undeliverable chat never leaves a half-configured setup, and it installs `xrayebator-monitor.timer`. That timer runs `monitor-check` every 15 minutes (`TimeoutStartSec=300` — the SNI probe can exceed the 90 s oneshot default, and a killed iteration would skip state finalization). What it watches: `xray.service`, `xrayebator-sub.service` (only if its unit exists) and `nginx.service` (only if enabled); installed backends — `hysteria-server.service` and `awg show awg0`, gated by the registry so a fresh server gets no phantom alerts; profile expiry (approaching within `ALERTS_EXPIRE_WARN_SEC` and already expired, aggregated into one signature so the message lists names); profiles disabled by a traffic limit; subscription liveness (loopback `:8080/sub/<token>` → 200 plus `vless://`/`hysteria2://`) and TLS-mode degradation (`http_tls`/`local_only` means Let's Encrypt could not validate http-01); a daily SNI probe over the SNIs profiles actually use (`ALERTS_SNI_INTERVAL_SEC`, `ALERTS_SNI_TIMEOUT`; same strict criterion as `probe-test` and SNI selection — `_sni_tls_output_ok_pure`, i.e. a completed TLS 1.3 handshake with a verified certificate, not the bare `Verify return code: 0`; curl HTTP code as fallback only when openssl is absent); and reboots via `boot_id` (edge-triggered). Dedup/retry state lives in `monitor-state.json`: a repeat of a bad event is not sent more often than `ALERTS_REMIND_SEC`, a recovery is a separate message, a failed send records no state so the next tick retries, the last SNI probe result is cached so retries and idle ticks never re-run the expensive probe (`--force-sni` forces it), and `boot_id` is persisted only after the reboot alert is delivered — otherwise that message would be lost forever. `_monitor_*` helpers are the test seams (`_monitor_boot_id`, `_monitor_awg_up`, `_monitor_sub_dir`, `_monitor_sub_local_base`, `_monitor_hysteria_unit`, `_monitor_sni_reachable`). Migration `alerts_monitor_2026` is registered in `main_menu`, `quickstart` and `happ-setup`; `uninstall.sh` disables the timer and removes the neutral root (the bot token lives there); it also tears installed backends down first (`hysteria-server.service`, `awg-quick@awg0`, the `awg0` interface, the AWG `modules-load.d` entry, the Hysteria binary/sysctl/deploy-hook), so no enabled unit survives with a deleted config — the AmneziaWG package and kernel module themselves stay. Guarded by `validation/test-alerts-monitor.sh`.
CLI JSON hygiene: `profile-create`/`profile-delete` **must** print only JSON on stdout. The shared helpers (`backup_config`, `add_inbound`, `open_firewall_port`, `safe_restart_xray`, `close_firewall_port`) print colored status lines that would corrupt the parse, so the CLI paths redirect stdout→stderr around those calls (`exec 3>&1; exec 1>&2 ... exec 1>&3`). Keep it that way when editing.

### HAPP profile vs GUI quickstart — a subtle case

`quickstart` **must** emit a multi-route profile with `xhttp-legacy` (schema_version 3, routes[] with 7 entries) — HAPP expects the multi-route shape. Do NOT create a single-route one-off profile; `_happ_ensure_default_multiroute_profile()` is the single source of truth for the HAPP profile and is shared by both `quickstart` and `happ-setup`. When debugging "HAPP shows no data", check that the profile in `/usr/local/etc/xray/profiles/*.json` has a `routes` array with 7 entries and that `xhttp-legacy` is one of them, and that the subscription body carries every route the profile has — including PQ routes on any transport (the HAPP body keeps `mlkem…` URLs; only the xhttp-specific drop rule is gone, see the subscription-formats bullet).
