# Xrayebator v0.7.1 — SSH brute-force protection, installs on the newest Xray and AWG on Debian 12

> An update for the server manager and the **Xrayebator Desktop GUI**. It installs over `0.7.0` and any `0.6.x` — migrations take care of the rest, no server needs to be reconfigured. If something goes wrong, post the logs in a comment here: logs are the fastest way to a fix.

## Changes since 0.7.0

18 commits: one new capability and five fixes without which a deployment broke on the newest kernels and distributions.

- **SSH brute-force protection** — the `ssh-protect` command, menu item `15`, the "Security and TLS" tab in the GUI, and automatic enablement on install and deploy.
- **The deploy address is exempt from bans for 24 hours** — `ignoreip` with an expiry stamp and a timer that removes it automatically.
- **A clean install on Xray 26.10.21+**: the installer no longer aborts during config validation.
- **The AmneziaWG PPA is added only together with its signing key** — previously it could leave `apt` broken.
- **AmneziaWG on Debian 12**: kernel headers are installed automatically, and a missing kernel turns into an explicit `reboot_required` instead of "could not install".
- **The GUI no longer swallows a backend failure** that arrives inside JSON.
- **AmneziaWG labelling**: "2.0" is gone everywhere, the 3.1 format is the default.

## In two words

A public SSH port on a VPN server is scanned constantly: on a live server we measured **9 953 failed logins in 24 hours from 115 addresses**, while `root` accepted passwords without any limit. In `0.7.1` protection is enabled automatically on install and deploy, toggled from a button in the GUI, and the address you deployed from is exempt from bans for a day — so a run of typos cannot lock you out.

The second half of the release is about installation: the new Xray-core (26.10+) stopped accepting our temporary config because of its file extension, the AmneziaWG PPA could be left without a signing key and break `apt`, and on Debian 12 the AmneziaWG module could not build because the running kernel had no headers.

## What's new

### 1. SSH brute-force protection

`xrayebator ssh-protect` (`--status`, `--enable`, `--disable`, `--unban IP`, `--quiet`) installs `fail2ban` with an `sshd` jail:

- 4 failures in 10 minutes → a 30-minute ban, repeat offenders escalate up to a day (`bantime.increment`);
- a `sshd_config.d/99-xrayebator-hardening.conf` drop-in with `MaxAuthTries 3` and `LoginGraceTime 30`;
- every knob sits **inside `[sshd]`**, so a fail2ban setup you already run with other jails keeps its defaults;
- the sshd config is validated with `sshd -t` before it is applied, and `ssh` reloads it — open sessions survive.

**Password authentication is deliberately kept**: the app manages the server as `root` over an SSH password, and key-only access remains a separate operator decision.

On the live server the failure rate dropped from ~415/hour to ≈72/hour within minutes; at the moment of the check 16 addresses were banned.

### 2. A day without bans for the deploy address

When protection is enabled, the address the install or deploy came from goes into `ignoreip` for 24 hours: an expiry stamp is written next to it, and `xrayebator-ssh-ignoreip.timer` (every 30 minutes) removes the entry once the term is over. Four typos in a password no longer lock you — or the GUI, which connects from the same address — out for half an hour. The loopback line `ignoreip = 127.0.0.1/8 ::1` stays permanently.

Verified live: six wrong passwords from the exempted address left the fail2ban counters at zero and produced no ban.

### 3. The security card in the GUI

The "Security and TLS" tab next to the subscription: state (`enabled` / `disabled`), the effective sshd limits, failed logins over 24 hours, how many addresses are banned and which ones, plus "Enable/Disable" and "Refresh". The ban exemption is not shown in the interface — it is a service detail, visible in `ssh-protect --status`.

## What's fixed

### 1. A clean install on Xray 26.10+

`install.sh` validated a temporary config named `config.json.tmp.XXXXXX`; since 26.10 the kernel infers the format from the **file extension** and ignores `-format json`, so validation failed on every clean server: `main/confloader/external: unsupported config file extension`. The temp config is now created as `*.json`, the same fix is applied to both temp configs in `update.sh` (the DNS update there was silently skipped for the same reason), and a failure now prints the kernel's own reason instead of only "not validated".

### 2. The AmneziaWG PPA without a key broke `apt`

When `add-apt-repository` was absent, the installer wrote the `amnezia/ppa` repository line **without the signing key**. After that `apt-get update` returned `rc=100` and every `apt` operation broke — including the certbot plugin for DNS-01 — while `apt install amneziawg` stopped finding the package. The repository is now written only together with its key (`signed-by`), no key means no repository, and already-affected servers are repaired by the `awg_ppa_signed_2026` migration.

### 3. AmneziaWG on Debian 12

The package from the PPA was installed, but DKMS never built the module: Debian does not install kernel headers by default, and for a kernel older than the repository the exact `linux-headers-$(uname -r)` package is gone (live example: running `6.1.0-45`, the repo ships `47/50/53/54`). The installer now installs the headers itself; when only newer ones exist it builds against that kernel, **installs its image too** and answers `reboot_required: true` with both kernel names. After a reboot the same command finishes the setup. The manual build no longer symlinks the `linux-source` archive — it extracts the tree.

### 4. The GUI dropped a failure returned inside JSON

Backend operations only reacted to a thrown exception. A command that reported the reason inside JSON (`{ok:false, error}`) looked like "clicked — nothing happened": on a live server `awg-install` returned `reboot_required` with a clear message while the card stayed at "Not installed". The result is now checked and the server's message is shown in the interface.

### 5. The "AmneziaWG 2.0" label

The menu item, the submenu banner, the CLI help and the documentation called the backend "AmneziaWG 2.0" although the 3.1 format is the default. The label is neutral now, and the format version is stated where it helps.

## Stability and security

- `fail2ban` and the sshd drop-in are installed only on Debian/Ubuntu (they need `apt` and `systemd`); elsewhere the command reports `supported: false` and changes nothing.
- The jail does not touch other fail2ban jails, `sshd -t` is validated before applying, and `ssh` is reloaded rather than restarted.
- `ssh-protect --disable` removes the jail, the drop-in, the exemption and the timer; the `fail2ban` package stays (removing it is a separate decision).
- Installing AmneziaWG can no longer leave `apt` in a broken state.

## How well this is tested

- **45 Bash validations** in `validation/`, two of them new (`test-ssh-protect.sh`, `test-config-temp-json-suffix.sh`) plus an extended `test-awg-lifecycle.sh`.
- **174 unit tests** (173 green on Windows; the single red one is the known `shell-command` case without `/bin/sh`), `npm run typecheck`, `npm run build`.
- **Live runs**:
  - Ubuntu 22.04 (production server): protection enabled, 8/8 routes via `channel-test`, subscription 200, 16 addresses banned;
  - Ubuntu 24.04 (a clean install from scratch): `install.sh` → `quickstart` → 7/7 routes, then a PQ route → 8/8, every subscription body 200;
  - Debian 12: install, an AWG attempt before the reboot (`reboot_required`), then after the reboot the module was built, `awg0` came up, the 3.1 format was active (`HeaderProtectionKey`, `RandomTrailers`), a profile peer was issued and routes passed 7/7.
- Documentation checks: 0 broken links or anchors, 0 table mismatches, encoding clean.

Honest limitations: the AWG handshake with a real client was not re-run in this cycle (the interface, 3.1 parameters and the peer were verified); the subscription is slow on a 1-vCPU server — Clash takes up to ~14 s.

## Before you upgrade

### Server requirements

Unchanged: Debian 12/13 or Ubuntu 22.04/24.04, `bash`, `root`/`sudo`, `systemd`, `apt`.

### What to know

- **Protection is enabled automatically only on install and deploy.** On an already-deployed server it has to be enabled once after the update: `sudo xrayebator ssh-protect --enable`, or the button in the "Security and TLS" tab.
- **No breaking changes.** Password logins, ports, profiles and subscriptions stay as they are.
- **On a Debian server with an old kernel** the AWG install may require a reboot — the command says so explicitly (`reboot_required`).
- If you update a server that tracks `dev` via `xrayebator update`, it stays on `dev`; use `xrayebator update main` for the stable branch.

## How to upgrade

### Server

```bash
sudo xrayebator-update          # full project lifecycle
# or just the manager + core:
sudo xrayebator update
# and enable protection once, if it is not on yet:
sudo xrayebator ssh-protect --enable
```

### Xrayebator Desktop GUI

Download the installer from the release assets and install over the previous version — server data and settings are preserved.

## Build

Produced by the same workflow: Ubuntu (AppImage), macOS arm64 (dmg + zip), Windows (exe). Typecheck, unit tests and all 45 Bash validations run before the build.
