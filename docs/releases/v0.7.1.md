# Xrayebator v0.7.1 — защита SSH от перебора, установка на новом Xray и AWG на Debian 12

> Обновление серверного менеджера и **Xrayebator Desktop GUI**. Ставится поверх `0.7.0` и любой `0.6.x` — миграции доделают всё сами, перенастраивать серверы не нужно. Нашли проблему или есть логи — пишите комментарием к релизу: по логам чиним быстрее всего.

## Изменения с 0.7.0

18 коммитов: одна новая возможность и пять исправлений, без которых развёртывание ломалось на новых ядрах и дистрибутивах.

- **Защита SSH от перебора** — команда `ssh-protect`, пункт меню `15`, вкладка «Безопасность и TLS» в GUI и автовключение при установке и деплое.
- **Адрес деплоя не банится 24 часа** — `ignoreip` со сроком и таймер, который снимает исключение сам.
- **Чистая установка на Xray 26.10.21+**: установщик больше не падает на валидации конфига.
- **PPA AmneziaWG ставится только с ключом подписи** — раньше он мог оставить `apt` нерабочим.
- **AmneziaWG на Debian 12**: заголовки ядра доустанавливаются, а нехватка ядра приводит к понятному `reboot_required`, а не к «не удалось установить».
- **GUI больше не проглатывает отказ бэкенда**, пришедший в JSON.
- **Ярлык AmneziaWG**: «2.0» больше нигде не написано, формат 3.1 по умолчанию.

## Если объяснить в двух словах

Публичный SSH на VPN-сервере перебирают постоянно: на живом сервере мы замерили **9 953 неудачных входа за сутки со 115 адресов**, при этом `root` пускался по паролю без ограничений. В `0.7.1` защита ставится сама при установке и деплое, включается одной кнопкой в GUI, а адрес, с которого вы разворачивали сервер, сутки не банится — чтобы серия опечаток не заперла вас снаружи.

Вторая половина релиза — исправления установки: новая Xray-core (26.10+) перестала принимать наш временный конфиг из-за расширения файла, PPA AmneziaWG мог остаться без ключа и сломать `apt`, а на Debian 12 модуль AmneziaWG не собирался, потому что для запущенного ядра не было заголовков.

## Что нового

### 1. Защита SSH от перебора

`xrayebator ssh-protect` (`--status`, `--enable`, `--disable`, `--unban IP`, `--quiet`) ставит `fail2ban` с джейлом `sshd`:

- 4 неудачи за 10 минут → бан 30 минут, повторным нарушителям — дольше, максимум сутки (`bantime.increment`);
- drop-in `sshd_config.d/99-xrayebator-hardening.conf` с `MaxAuthTries 3` и `LoginGraceTime 30`;
- настройки живут **внутри `[sshd]`**, поэтому уже настроенный вами fail2ban с другими джейлами не меняется;
- конфиг sshd проверяется `sshd -t` до применения, `ssh` перечитывает его через `reload` — открытые сессии не рвутся.

**Парольный вход осознанно не выключается**: приложение управляет сервером как `root` по SSH-паролю, и режим «только ключи» остаётся отдельным решением оператора.

На живом сервере частота неудачных попыток упала с ~415/час до ≈72/час в первые же минуты; к моменту проверки в бане держалось 16 адресов.

### 2. Сутки без банов для адреса деплоя

При включении защиты адрес, с которого пришла установка или деплой, попадает в `ignoreip` на 24 часа: рядом пишется метка срока, а `xrayebator-ssh-ignoreip.timer` (каждые 30 минут) снимает исключение, когда срок вышел. Четыре опечатки в пароле больше не запирают вас (и GUI, который ходит с того же адреса) на полчаса. Loopback-строка `ignoreip = 127.0.0.1/8 ::1` остаётся навсегда.

Проверено на живом сервере: шесть неверных паролей с исключённого адреса — счётчики fail2ban остались нулевыми, бана нет.

### 3. Карточка защиты в GUI

Вкладка «Безопасность и TLS» рядом с подпиской: состояние (`включена` / `выключена`), действующие лимиты sshd, число неудачных входов за сутки, сколько адресов в бане и какие именно, кнопки «Включить/Выключить» и «Обновить». Исключение из банов в интерфейсе не показывается — это служебная деталь, видно в `ssh-protect --status`.

## Что исправлено

### 1. Чистая установка на Xray 26.10+

`install.sh` валидировал временный конфиг с именем вида `config.json.tmp.XXXXXX`; начиная с 26.10 ядро определяет формат **по расширению файла** и игнорирует `-format json`, поэтому валидация падала на любом чистом сервере: `main/confloader/external: unsupported config file extension`. Теперь временный конфиг создаётся как `*.json`, тот же приём применён к двум временным конфигам в `update.sh` (там из-за этого молча пропускалось обновление DNS), а при провале печатается вывод ядра, а не только «не прошёл валидацию».

### 2. PPA AmneziaWG без ключа ломал `apt`

Если в системе не было `add-apt-repository`, установщик писал строку репозитория `amnezia/ppa` **без ключа подписи**. После этого `apt-get update` возвращал `rc=100` и ломался любой `apt` — включая установку плагина certbot для DNS-01, — а `apt install amneziawg` переставал находить пакет. Теперь репозиторий пишется только вместе с ключом (`signed-by`), нет ключа — нет репозитория, а уже испорченные серверы чинит миграция `awg_ppa_signed_2026`.

### 3. AmneziaWG на Debian 12

Пакет из PPA ставился, но DKMS не собирал модуль: Debian не ставит заголовки ядра по умолчанию, а для ядра, которое старше репозитория, точного пакета `linux-headers-$(uname -r)` уже нет (живой пример: запущено `6.1.0-45`, в репозитории `47/50/53/54`). Установщик теперь ставит заголовки сам; если доступны только новые — собирает модуль под новое ядро, **ставит и его образ** и отвечает `reboot_required: true` с обоими именами ядер. После перезагрузки та же команда завершает настройку. Ручная сборка больше не линкует архив `linux-source`, а распаковывает дерево.

### 4. GUI терял отказ, пришедший в JSON

Операции с бэкендами реагировали только на выброшенное исключение. Команда, которая сообщала причину внутри JSON (`{ok:false, error}`), выглядела как «нажал — ничего не произошло»: на живом сервере `awg-install` вернул `reboot_required` с понятным текстом, а карточка осталась «Не установлено». Теперь результат проверяется и текст сервера показывается в интерфейсе.

### 5. Ярлык «AmneziaWG 2.0»

Пункт меню, баннер подменю, справка CLI и документация называли бэкенд «AmneziaWG 2.0», хотя формат 3.1 включён по умолчанию. Теперь ярлык нейтральный, а версия формата указана там, где полезна.

## Стабильность и безопасность

- `fail2ban` и drop-in sshd ставятся только на Debian/Ubuntu (нужны `apt` и `systemd`); на остальных системах команда возвращает `supported: false` и ничего не меняет.
- Джейл не трогает чужие джейлы fail2ban, `sshd -t` проверяется до применения, `ssh` перезапускается через `reload`.
- `ssh-protect --disable` снимает джейл, drop-in, исключение и таймер; пакет `fail2ban` остаётся (его удаление — отдельное решение).
- Установка AmneziaWG больше не может оставить `apt` в нерабочем состоянии.

## Насколько это проверено

- **45 Bash-валидаций** (`validation/`), из них две новые: `test-ssh-protect.sh` и `test-config-temp-json-suffix.sh`, плюс расширенный `test-awg-lifecycle.sh`.
- **174 unit-теста** (173 зелёных на Windows; единственный красный — известный кейс `shell-command` без `/bin/sh`), `npm run typecheck`, `npm run build`.
- **Живые прогоны**:
  - Ubuntu 22.04 (продакшн-сервер): защита включена, 8/8 маршрутов `channel-test`, подписка 200, 16 адресов в бане;
  - Ubuntu 24.04 (чистая установка с нуля): `install.sh` → `quickstart` → 7/7 маршрутов, затем PQ-маршрут → 8/8, все тела подписки 200;
  - Debian 12: установка, попытка AWG до перезагрузки (`reboot_required`), после перезагрузки — модуль собран, `awg0` поднят, формат 3.1 (`HeaderProtectionKey`, `RandomTrailers`), пир профиля выдан, маршруты 7/7.

Честные ограничения: рукопожатие AWG живым клиентом в этом цикле не перепроверялось (проверены интерфейс, параметры 3.1 и пир); подписка на слабом 1-vCPU сервере отдаётся медленно — Clash до ~14 с.

## Важно перед обновлением

### Требования к серверу

Без изменений: Debian 12/13 или Ubuntu 22.04/24.04, `bash`, `root`/`sudo`, `systemd`, `apt`.

### Что стоит знать

- **Защита SSH включается автоматически только при установке и деплое.** На уже развёрнутом сервере после обновления её нужно включить один раз: `sudo xrayebator ssh-protect --enable` или кнопкой во вкладке «Безопасность и TLS».
- **Break changes нет.** Парольный вход, порты, профили и подписки не меняются.
- **Если сервер на старом ядре Debian**: установка AWG может потребовать перезагрузки — команда скажет это прямым текстом (`reboot_required`).
- Если вы обновляете сервер с ветки `dev` командой `xrayebator update`, ветка останется `dev`; для стабильной — `xrayebator update main`.

## Как обновиться

### Сервер

```bash
sudo xrayebator-update          # полный жизненный цикл проекта
# или только менеджер + ядро:
sudo xrayebator update
# и один раз включить защиту, если она ещё не включена:
sudo xrayebator ssh-protect --enable
```

### Xrayebator Desktop GUI

Скачайте установщик из ассетов релиза и поставьте поверх — данные и настройки серверов сохраняются.

## Сборка

Собирается тем же workflow: Ubuntu (AppImage), macOS arm64 (dmg + zip), Windows (exe). Перед сборкой прогоняются typecheck, unit-тесты и все 45 Bash-валидаций.
