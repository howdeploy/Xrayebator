# Xrayebator 0.7.3 -- secrets out of process arguments, snap-certbot fix, Hysteria self-recovery

**Date:** 2026-11-07
**Previous release:** `0.7.2` (2026-11-04)
**Xray-core:** `26.10.31` (unchanged)

A patch release driven by three consecutive live runs: Debian 13, Ubuntu 24.04 and Ubuntu 22.04.
The headline is that secrets no longer travel through process command lines, plus two defects that
broke real servers (a fresh Ubuntu 24.04 image and a damaged backend).

## What was wrong

### 1. Tokens in process arguments (security)

`/proc/<pid>/cmdline` is readable by **every** local user (`0444`), while
`/proc/<pid>/environ` is readable only by the process owner and root (`0400`). Until this release
three groups of credentials travelled as arguments, so any local account could read them -- including
the `xray` service account the proxy itself runs under.

Confirmed on live servers (read as the unprivileged `xray` user, uid 999):

```
/bin/bash /usr/local/bin/xrayebator alerts-setup --token 999999999:AAFake... --chat-id 123456
curl -sS --max-time 20 https://api.telegram.org/bot999999999:AAFake.../getMe
/bin/bash /usr/local/bin/xrayebator dns01-setup --domain ... --token AAFakeDns...
```

The bot-token exposure was not one-off: `xrayebator-monitor.timer` runs its check every 15 minutes,
so a process with the token on its command line existed on every tick.

### 2. `quickstart` could not find certbot on a fresh Ubuntu 24.04

On a clean image deployment ended with
`{"ok":false,"error":"Certbot <with --ip-address and --preferred-profile> not found"}`, while a manual
`snap install --classic certbot` installed 5.9.0 at that very moment. Cause: `snapd` on 24.04
finishes seeding and restarts itself right after boot ("Waiting for automatic snapd restart..."), and
the install ran through a duplicate code path in quickstart with `2>/dev/null || true`, swallowing
the failure.

### 3. Hysteria 2 did not recover from a damaged install

When the registry still said `installed` but the binary was gone (failed update, manual cleanup),
`hysteria2-install` answered `{"ok":true,"already":true}` and did nothing, while `hysteria2-status`
honestly reported `binary: "absent"`. There was no repair path.

### 4. Smaller issues found by the same run

* `xrayebator channel-test` without `--name` answered "specify a profile name" (in Russian) even with
  exactly one profile: `HAPP_DEFAULT_PROFILE` is only set inside a quickstart process.
* `quickstart` mixed coloured firewall lines into stdout, so
  `xrayebator quickstart --without-email | jq .ok` failed.

## What changed

### Security

* URLs carrying a token are handed to `curl` through a stdin config (`-K -`), so the bot token and
  the subscription `sub_token` no longer appear in `argv`.
* `jq` receives secret values through the environment (`$ENV.XRAYEBATOR_JQ_SECRET`) instead of
  `--arg`: that covers the Hysteria 2 password, AmneziaWG keys, `sub_token`, the VLESS Encryption
  key and the bot token when they are written into JSON.
* Commands accept the credential itself on stdin or from a file:
  `--secret-file PATH` / `--secret-stdin` (quickstart uses `--dns01-secret-file` /
  `--dns01-secret-stdin`). A file wider than `0600` is refused and deleted right after reading.
  `--token` and `--aws-secret-access-key` still work but warn on stderr.
* The desktop GUI sends DNS-01 credentials as a `0600` file over SFTP, so the token reaches neither
  the local nor the remote command line.

```bash
# Before (visible in /proc for the whole 30+ s issuance):
sudo xrayebator dns01-setup --domain sub.example.com --provider cloudflare --token "$CF"

# After:
printf 'token=%s\n' "$CF" | sudo xrayebator dns01-setup \
  --domain sub.example.com --provider cloudflare --secret-stdin --email you@example.com
```

### Fixes

* **certbot for IP certificates** is installed by the single `_ensure_certbot_ip_tls` helper: it
  waits for snapd readiness (`snap wait system seed.loaded`), retries three times, verifies the
  result by the binary's actual flags (not by snap's exit code) and logs to `/tmp/snap-*.log`
  instead of stdout.
* **Hysteria 2 self-recovers**: install checks for the binary, the unit and `server.yaml`, and when
  any is missing it drops the registry entry and takes the normal install path; an orphaned unit is
  stopped before the port check (otherwise recovery hit "UDP port 443 already in use").
* `channel-test` without `--name` uses the only profile in the system; with several profiles it
  still asks for a name rather than guessing.
* Firewall statuses and snap progress go to stderr, so CLI stdout is pure JSON again.

### Tests

* New `validation/test-secret-argv.sh`: a stub `curl` proves the secret is absent from `argv` and
  present on stdin, plus payload parsing for `--secret-file`/`--secret-stdin` and refusal of a file
  wider than `0600`.
* New `validation/test-certbot-snap-ip.sh`: a single install path, snapd readiness, retry, and
  capability-based verification.
* `test-hysteria2-lifecycle.sh` and `test-awg-lifecycle.sh` are now hermetic: the manager's paths
  (`HYSTERIA2_BIN`, `HYSTERIA2_UNIT_FILE`, `AWG_SYSCTL_FILE`, `AWG_MODULES_LOAD_FILE` and friends)
  are overridable and the tests redirect them into a temp dir. Previously running the suite on a
  live server **deleted the real** `/usr/local/bin/hysteria`, and the "module for a foreign kernel"
  check degenerated into "module for this same kernel" on a host running `5.15.0-177`.
* `test-channel-test-cli.sh` anchors on an ASCII line instead of the box-drawing character `-`,
  which `mawk` (the default awk on Debian/Ubuntu) does not match.
* **49** Bash validations in total (was 47).

## Verified live

| Platform | What was run | Result |
|---|---|---|
| Ubuntu 22.04.5, kernel 5.15.0-177 | GUI wizard (`Deployer`), keys page, protocols page, server settings, server import -- the real `src/main/core/*` code | **37/37** |
| Ubuntu 22.04.5 | `validation/` in a clean environment | **49/49** |
| Ubuntu 22.04.5 | routes, subscription, limits, expiry, Hysteria 2 and AmneziaWG end-to-end tunnels | 7/7 routes, 4 bodies 200, Hysteria 3/3 requests, AWG ping 3/3 |
| Ubuntu 24.04.4 | install 0.7.2 -> `update dev` -> deploy, routes, backends, reboot | 7/7 routes, everything came back after reboot |
| Debian 13 | the same plus AWG from the Ubuntu PPA, kernel-guard, certificate renewal | unchanged from 0.7.2 |

Additionally verified on live servers:

* the secret leak was **reproduced** on 0.7.2 (2 processes with the bot token, 1 with the DNS token
  in `/proc`, read as the unprivileged `xray` user) and is **absent** on 0.7.3 (0 processes);
* Hysteria self-recovery: deleting `/usr/local/bin/hysteria` with the registry intact ->
  `hysteria2-install --grant-all` restored the binary (23.9 MB), unit `active`, UDP socket bound;
* `kernel-guard`: three `--enable` calls produce exactly one nft rule, MPTCP is off, and the
  protection survives a reboot.

## Upgrading

```bash
sudo xrayebator-update          # full lifecycle path
# or just the manager:
sudo xrayebator update main
```

Rollback is compatible in both directions: the server-side `--token`/`--aws-secret-access-key`
options are still there, so an old GUI works with an old server and a new GUI works with both.

**Worth one check after upgrading** if a backend ever failed to update:

```bash
sudo xrayebator backend-status        # installed and state are reported separately
sudo xrayebator hysteria2-install     # now repairs a damaged install itself
```
