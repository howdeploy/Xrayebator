# Частые проблемы

[← Назад к README](../../README.ru.md) · [English](../troubleshooting.md) · [简体中文](../zh-CN/troubleshooting.md)

---

## HAPP не обновляет подписку

JSON, выдаваемый `quickstart`, содержит `subscription_url`. Он строится из сохранённой базы, поэтому
хост и порт в URL осознаны:

```text
https://your-domain/sub/<token>        # public TLS на 443
https://your-domain:8443/sub/<token>   # public TLS на 8443
http://127.0.0.1:8080/sub/<token>      # local-only debug режим
```

Проверьте актуальный URL с VPS, сохранив его порт:

```bash
curl -vkI https://your-domain[:port]/sub/
curl -vk https://your-domain[:port]/sub/<token>
```

`/sub/` без токена должен вернуть `404`. Полный URL токена — `200` и тело со ссылками `vless://`.
Затем сервисы:

```bash
systemctl status xrayebator-sub --no-pager -l
systemctl status nginx --no-pager -l
```

Если у URL неверный хост или порт, посмотрите режим подписки и повторите настройку IP-TLS или
домена; добавление DNS-записи само не переписывает сохранённые маркеры endpoint.

## URL показывает 127.0.0.1

Включён local-only режим; он только для отладки или SSH-туннеля. Для телефона включите
`Подписка HAPP` → public TLS по IPv4 или по домену. Local URL нельзя передавать внешнему клиенту.

## IP-TLS не работает на IPv6-only VPS

Автоматический IP-сертификат в current flow требует публичного IPv4. Он отказывается выпускать
IPv6 IP-TLS endpoint, потому что этот путь не автоматизирован. Настройте домен с достижимой A/AAAA и
используйте доменный TLS-режим.

## URL показывает IP, хотя домен уже добавлен

DNS-запись — не сохранённая конфигурация подписки. Заново включите доменный режим:
`Подписка HAPP` → public TLS по домену. Проверьте, что `subscription_url` использует домен и включает
`:8443`, если публичный listener не на 443.

## `happ-setup` отказывается возвращать публичный URL

Это проверка безопасности, а не отсутствие опции форматирования URL. `happ-setup` не фабрикует
публичный endpoint из IP или marker-файла. Он требует, чтобы vhost подписки, сертификат и активный
HTTPS-listener были подтверждены перед записью/выдачей публичного URL, когда маркеры отсутствуют; если
сохранённые маркеры устарели, правильные значения (домен/порт) могут остаться.

Если это новый сервер, сначала выполните `quickstart --email <address>` или настройте HAPP IP/домен из
терминального меню. Для существующей установки проверьте:

```bash
sudo systemctl status nginx --no-pager -l
sudo systemctl status xrayebator-sub --no-pager -l
sudo journalctl -u xrayebator-sub -n 80 --no-pager
```

Почините сертификат или listener, затем снова `sudo xrayebator happ-setup`. Не обходите ошибку
вручную написанным публичным URL.

## HAPP показывает шесть маршрутов, хотя в профиле семь

Это ожидаемо для managed HAPP-профиля. Профиль JSON должен содержать семь живых `routes[]`,
включая `xhttp-legacy` и `xhttp-pq`; публикуемый VLESS-список содержит шесть записей, потому что
PQ-XHTTP маршрут сохраняется для raw/profile path, а не для обычного HAPP-списка.

Проверьте профиль и живые порты:

```bash
jq -r '.routes[] | [.label,.transport,.port,(.pq_enabled // false)] | @tsv' \
  /usr/local/etc/xray/profiles/<profile>.json
```

Последняя колонка — `pq_enabled`, а не health-статус. `false` ожидаем для всех не-PQ маршрутов;
`true` должен быть только у `xhttp-pq`. Обратите внимание: этап `_migrate_happ_legacy_xhttp_route_2026`
не добавляет маршруты в существующие профили. Если `xhttp-legacy` отсутствует в существующем профиле,
заново создайте/восстановите managed multi-route профиль (re-provision через меню/quickstart или
создайте заново), а не просто прогоняйте миграции.

## XHTTP в HAPP не работает

HAPP-совместимый XHTTP-кандидат — `xhttp-legacy`, а не PQ-маршрут. После обновления запустите
`sudo xrayebator`, дайте миграциям завершиться и принудительно обновите подписку в HAPP. Убедитесь,
что маршрут есть в профиле, а его порт — в живом конфиге.

## v2rayNG то подключается, то нет

`v2rayNG` не основной клиент HAPP-флоу. Он получает v2ray-совместимый body, но маршруты всё равно
зависят от поддержки транспорта и версии Xray-core внутри клиента. Проверяйте маршруты по отдельности:
универсального порядка «лучший → худший» нет.

## После смены SNI, порта или fingerprint подключение умерло

Обновите подписку в клиенте или заново получите raw route. SNI и порт — общие настройки инбаунда,
поэтому их изменение может затронуть все профили на этом порту и обычно требует переподключения клиента.
Fingerprint — клиентский по выбранному профилю/маршруту, не перезапускает Xray и не меняет другие
маршруты. Серверная подписка меняется сразу, но HAPP нужно обновить принудительно или дождаться
очередного автообновления.

## Подписка возвращает 410, хотя профиль выглядит рабочим

Профиль отключён по сроку действия: в profile JSON стоит `.expire_disabled: true` либо `.expire`
(epoch-секунды) уже в прошлом. Принуждение выполняет systemd-таймер `xrayebator-expire.timer`
(каждые 10 минут, `xrayebator expire-check`): он снимает клиента с inbound'ов, поэтому подключиться
нельзя даже по уже скачанной ссылке, а подписка отвечает `410 Gone` с телом `Profile expired or
disabled`. Если при выборе срока указана только дата (например, 30 сентября), профиль действует весь
этот день и истекает в `23:59:59` по локальным часам сервера; явное время из CLI также трактуется в
часовом поясе сервера. Продлите срок или снимите его:

```bash
sudo xrayebator profile-expire --name ИМЯ --expire 2026-12-31   # продлить
sudo xrayebator profile-expire --name ИМЯ --expire none         # сделать бессрочным
```

Продление возвращает того же клиента (тот же uuid), поэтому устройствам не нужно переимпортировать
подписку. В GUI то же самое делается кнопкой «Срок» на карточке профиля.

## На сервере есть старые профили, но они не работают

Если profile JSON указывает на порты, которых уже нет в `config.json`, это устаревший профиль. Новая
подписка такие маршруты не отдаёт. `410 Gone` возвращается только когда у профиля не осталось живых
маршрутов; частично устаревший multi-route может вернуть `200` с оставшимися рабочими маршрутами.
Пересоздайте профиль или почините живой инбаунд через терминальное меню; не публикуйте ссылку на
мёртвый порт.

## Подключение с клиента не работает

Причины по порядку:

1. HAPP устарел — обновитесь до `3.3.6` или новее, полностью закройте все старые процессы HAPP,
   запустите ровно один актуальный экземпляр и обновите подписку.
2. Зелёный ping маршрута не подтверждает работу основного TUN: HAPP проверяет маршруты отдельным
   временным Xray-core. На Linux `ss -lntp | grep ':10808'`; пустой вывод означает, что основной core
   не слушает, поэтому полностью перезапустите HAPP.
3. Клиент не поддерживает транспорт — начните с subscription URL или TCP-маршрутов.
4. SNI не подходит — проверьте его через `sudo xrayebator probe-test` и замените.
5. Порт блокируется провайдером — смените порт профиля.
6. Fingerprint детектируется — попробуйте `firefox` вместо `chrome`.
7. Подписка устарела — убедитесь, что маршрут есть в живом `config.json`.

Xrayebator 3.0 также однократно удаляет установленное старыми версиями правило блокировки UDP/443.
Оно могло ломать Telegram при зелёном TCP-пинге маршрута. Пользовательские routing-правила с
дополнительными условиями сохраняются.

Держите наготове 2-4 профиля, чтобы переключаться в экстренной ситуации.

## Обновление через GUI не выполнило полное обновление проекта

Server Settings в Electron-GUI вызывает `xrayebator update <branch>`: он self-update'ит менеджер из
ветки и обновляет Xray-core. Это не `xrayebator-update [branch]`, полный lifecycle-updater. Запустите
последний из SSH-терминала, когда нужно обновить данные, интеграцию подписки и все lifecycle-шаги.

GUI намеренно предоставляет только подмножество Bash-меню. Используйте терминал для `probe-test`,
HAPP setup, каскада, self-steal и журналов/статуса сервиса; сроки действия профилей и отзыв
подписки настраиваются в разделе «Настройки сервера», bypass остаётся терминальной/CLI-операцией.

## Electron unit-тест падает на Windows

`tests/unit/shell-command.test.ts` намеренно вызывает POSIX `/bin/sh`. Нативный Windows такого пути не
даёт, поэтому этот один shell-специфичный тест может падать локально, даже когда TypeScript
валиден. Запускайте полный Electron unit-suite на Linux или в Ubuntu CI-job; Linux — источник истины для
этого POSIX-поведения. Активный Electron release-workflow также запускает unit-тесты на Ubuntu перед
сборкой Windows, macOS и Linux.

## Меня выкинуло с сервера во время настройки

Если подключиться к своему же VPN и затем менять что-то на сервере, SSH может оборваться. Самое
простое — заходить на сервер не через собственный маршрут. Можно добавить keep-alive:

```bash
sudo nano /etc/ssh/sshd_config
```

```text
ClientAliveInterval 60
ClientAliveCountMax 120
TCPKeepAlive yes
```

```bash
sudo systemctl restart sshd
```

## Пропал доступ ко всему интернету

Проверьте DNS на клиенте. При блокировках VPN-провайдеров DNS ломается первым. Держите на клиенте
список альтернативных ссылок подписки. На настольных клиентах проверьте, включён ли TUN-режим, если
он нужен для системного проксирования.

## Сколько пользователей можно подключить

Жёсткого лимита профилей в интерфейсе нет. Реальная ёмкость упирается в CPU, RAM, канал VPS, число
маршрутов и лимиты провайдера. Наращивайте число пользователей постепенно и следите за нагрузкой.

Несколько профилей одновременно использовать можно: разные подписки, SNI, порты и маршруты дают
больше вариантов обхода блокировок, но делят общие ресурсы VPS.

## Сервис Hysteria 2 не стартует

Сначала причина — установка откатывает артефакты, состояние нужно воспроизвести:

```bash
journalctl -u hysteria-server.service --no-pager | tail -20
```

Известные режимы отказа (в генераторе исправлены, актуальны при ручной правке конфигов):

- `invalid config: auth.userpass: empty auth userpass` — ключ auth-карты называется `userpass`, а
  **не** `users`, и пустая карта отвергается. Генератор всегда рендерит хотя бы
  `_xrayebator_placeholder`, пока ни у одного профиля нет гранта; при ручной правке `server.yaml`
  держите под `userpass:` непустую карту.
- `Changing to the requested working directory failed: Permission denied` — каталог бэкенда должен
  быть `root:hysteria 0750`; `chmod` без парного `chown` оставляет `root:root`, и юнит не может
  войти в каталог.
- Сертификат нечитаем — в режиме `le` это копии с владельцем `root:hysteria 0640`; renewal
  deploy-hook обновляет их при продлении.

После исправления чистый путь: `hysteria2-uninstall`, затем свежий `hysteria2-install`.

## AWG: интерфейс поднят, но нет `latest handshake`

AmneziaWG сообщает о несовпадении параметров молчанием: peer просто никогда не получает хендшейк.
Проверьте группу «должны совпадать» — она обязана быть идентичной на сервере и в каждом клиентском
`.conf`:

- `S1`–`S4` (≥ 12 для движков 3.x), `H1`–`H4`;
- 3.x-ключи, если они есть на другой стороне: `HeaderProtectionKey` (3.0) и `RandomTrailers` (3.1)
  совпадают побайтово. Xrayebator эмитит их только в режиме 3.1 (`awg-31 --on`, для новых установок
  включён по умолчанию); несовпадение обычно означает, что клиентский `.conf` старше переключения
  на 3.1 — перекачайте его — либо смешан с чужим/ручным конфигом;
- версия клиентского приложения: конфиги с `RandomTrailers` требуют AmneziaVPN ≥ 5.0.1.5; более
  старые могут отказаться импортировать конфиг целиком.

Затем разделите зоны отладки: `awg show awg0` на сервере — если peer в списке, хендшейк есть, а
трафика нет, проблема в зоне `awg-quick`/маршрутизации/firewall (`ip_forward`, интерфейс
MASQUERADE), а не в параметрах протокола.

Прежде чем винить параметры, проверьте сам сетевой путь. Сокет AWG живёт в ядре, поэтому UDP-порт
не виден в `ss`/`netstat` — увидеть что-либо можно только захватом на сервере в момент, когда
клиент пытается подключиться:

```bash
tcpdump -l -ni <iface> 'udp port <port>'
```

Пусто → пакеты не доходят вовсе: фильтрация оператора/DPI (типичный паттерн РФ — Hysteria 2 на
UDP 443 проходит, а высокий случайный UDP-порт молча дропается). Захват показывает пакеты, а
`awg show` по-прежнему без хендшейка → клиент шлёт «мусор»: перевыпустите `.conf`, проверьте
версию приложения (3.1-параметры требуют AmneziaVPN ≥ 5.0.1.5) или временно `awg-31 --off` и
переимпортируйте для проверки 2.0-совместимости. Учтите: `tcpdump` без `-l` при перенаправлении в
файл блочно-буферизует вывод — ранние пакеты могут не появиться до сброса буфера.

## AmneziaVPN (полное приложение) падает с ошибкой 1000, standalone-клиент работает

`ошибка 1000` — зонтичный `AndroidError` приложения; в логе телефона при этом
`VPN config format error: No value for client_ip`. Нативный конвейер приложения принимает только
свой формат экспорта — контейнер `amnezia-awg2`, серверные junk-поля рядом с `last_config`,
`protocol_version` и сжатый (`qCompress`) payload. Сырой `.conf` (или голый `vpn://` без этих
полей) сохраняется, но клиентская часть до туннеля не доходит. Код «QR · AmneziaVPN» в десктоп-GUI
собирает ровно этот shape — используйте его вместо вставки `.conf`. Junk-группа, которую ставит
Xrayebator, повторяет дефолты Amnezia (`Jc` 5, `Jmin` 10, `Jmax` 50, `H1`–`H4` = 1..4) именно
потому, что их go-туннель применяет кастомный junk не целиком.

## Установка AWG падает

- Основной путь — PPA `amnezia/ppa`; на сериях дистрибутива без сборок PPA Xrayebator уходит в
  сборку из исходников. Для ядер ≥ 5.6 нужен **полный** пакет `linux-source` — одних заголовков
  недостаточно (сборка модуля линкует всё дерево исходников).
- Проверка после установки: `lsmod | grep amneziawg` показывает модуль, `awg --version` отвечает.
- Юнит `awg-quick@awg0` читает `/etc/amnezia/amneziawg/awg0.conf` — Xrayebator держит его как
  symlink на `/usr/local/etc/xrayebator/backends/awg/awg0.conf`. Удаление symlink ломает юнит,
  хотя сам конфиг бэкенда валиден.
- При uninstall пакеты и kernel-модуль намеренно остаются в системе; удаляются интерфейс, конфиг,
  symlink и правило firewall.

## В подписке нет строки `hysteria2://`

Ссылки `hysteria2://` добавляются в оба тела подписки только при выполнении всех условий:

1. бэкенд Hysteria 2 установлен (`xrayebator hysteria2-status`);
2. у профиля есть грант (JSON `profiles` → `.backends.hysteria2.password`);
3. флаг реестра `sub_body` равен `true` (выключатель — меняется в `backends.json`, handler
   перечитывает реестр на каждый запрос, рестарт сервиса не нужен).

Истёкший или отключённый профиль строки не получает; у отозванного на следующей загрузке подписки
новый credential. `404` на ранее работавший токен после revoke — ожидаемо: сам токен ротирован.

## quickstart падает с «apt-get install nginx failed»

На свежем Ubuntu-VPS `unattended-upgrades` может держать apt/dpkg lock около 10 минут и вызывать `dpkg` отдельно для каждого пакета, поэтому простая проверка lock проскакивает в зазор между пакетами. quickstart теперь дополнительно ждёт активного воркера `unattended-upgrade` (бюджет 12 минут) и передаёт `apt-get install` опцию `-o DPkg::Lock::Timeout=180`. Повторите деплой, когда quickstart сообщит, что apt занят дольше бюджета, или дождитесь окончания очереди. Поведение закреплено в `validation/test-apt-lock-race.sh`.

## quickstart пишет «certbot failed: ... Connection reset by peer», но завершается успешно

Let's Encrypt не смог скачать http-01 challenge — чаще всего сеть хостера фильтрует
порт 80 для зарубежных источников (проверено tcpdump'ом и мультиузловыми пробами:
наш firewall и nginx исправны, reset происходит upstream). С этим деградационным
режимом деплой завершается в fallback `http_tls`: итоговый JSON несёт `degraded:true`
и `tls_mode:"http_tls"`, GUI показывает сервер как «Настроен частично», ключи
загружаются по SSH. Публичного URL подписки в этом режиме нет вовсе —
уязвимой HTTP-ссылки не появляется. Чтобы вернуть HTTPS, попросите хостера разблокировать порт 80 для
validation-диапазонов Let's Encrypt (или направьте домен на сервер и используйте
доменный TLS-режим), затем повторите деплой — он идемпотентен и выпустит LE-серт,
когда challenge станет доступен. Структуру fallback закрепляет
`validation/test-quickstart-tls-fallback.sh`.
