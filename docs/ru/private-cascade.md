# Приватный каскад через российский VPS

[← Назад к README](../../README.ru.md) · [English](../private-cascade.md) · [简体中文](../zh-CN/private-cascade.md)

## Схема

Нужны два VPS. Клиент подключается к российскому узлу. Узел применяет одинаковую политику к TCP и поддерживаемому прикладному UDP: выбранные российские ресурсы выходят из России, заблокированные и не совпавшие с российскими правилами — через зарубежный VPS по VLESS REALITY.

| VPS | Роль | Какой адрес нужен |
|---|---|---|
| Входной в России, например в Москве | Принимает клиентов и выпускает явно выбранный трафик из России | Публичный адрес, доступный клиентам, и известный стабильный исходящий адрес для связи с зарубежным VPS |
| Выходной за рубежом | Принимает соединение от российского VPS и выпускает переданный трафик в интернет | Публичный адрес подключения, доступный из России, и рабочий выход к ресурсам, которые нужны клиентам |

Для этих ролей достаточно одного публичного IPv4 на каждый VPS. Зарубежный узел может принимать соединение и выпускать трафик с одного адреса. В полной схеме из статьи зарубежные адреса приёма и выхода дополнительно разделены через второй IP, шлюз или WARP. Для российских ресурсов автор делает явное исключение. При прямом маршруте такой ресурс видит публичный IP входного узла. Объяснение автора о том, как узнают и блокируют адреса, остаётся гипотезой. [Статья на Хабре, раздел 4](https://habr.com/ru/articles/1103460/)

## Перед изменениями на VPS

1. Проверьте условия обоих хостингов для предполагаемого использования прокси. Запишите фактические публичные адреса, исходящий IP, который зарубежный VPS увидит с учётом NAT провайдера, порты и способ входа через аварийную консоль. Сверьте ключи SSH-серверов по независимому источнику. Поддерживаемые ОС перечислены в [рекомендациях по VPS](recommendations.md#выбор-vps).
2. Убедитесь, что клиентская сеть достаёт до российского слушателя по IPv4. Между серверами используйте IPv4 с ограничением доступа по источнику или IPv6, если на всём пути работают маршрут, слушатель и правила firewall. Если клиентам нужны IPv4-ресурсы, отдельно проверьте, что зарубежный VPS до них достаёт.
3. Зафиксируйте текущие маршруты и профили Xray, бэкенды, слушатели и правила firewall на хостах и у провайдеров. Сделайте защищённые резервные копии или снимки и держите открытым отдельный сеанс администрирования. Если подготовка любого из узлов требует перезапуска действующей службы или изменения её порта, работайте в окно обслуживания.
4. Выделите отдельный TCP-порт на зарубежном VPS. В firewall провайдера разрешите подключения к этому порту только с фактического исходящего адреса российского VPS (`/32` для IPv4 или `/128` для IPv6). На самом хосте задайте такое же ограничение и проверьте отсутствие более широких разрешений, в том числе созданных Xrayebator. Сохраните правила для SSH, подписок и существующих клиентских портов. Ограничьте порт у провайдера до создания входящего подключения Xray, поскольку менеджер может открыть порт в UFW.
5. Используйте отдельные данные доступа по SSH, пары ключей REALITY и ключи сертификатов для каждого VPS. Создайте отдельный VLESS UUID для связи между узлами. Клиентам выдавайте только профиль российского входа. Ссылку или UUID зарубежного узла храните на двух VPS, которым они нужны. Дайте токенам DNS минимальные права и храните их в файлах, доступных только root. Убирайте ссылки и токены из журналов и отчётов.

На чистых VPS установите Xrayebator на обоих узлах. Этот пример использует Xray и локальный UDP-обработчик на стандартной библиотеке Python 3 на входном узле; дополнительные VPN-бэкенды не нужны. Если на одном из узлов уже установлены дополнительные протоколы, после создания профиля проверьте выданный ему доступ. Xrayebator передаёт события создания и удаления профиля установленным бэкендам. [Установка](../../README.ru.md#установка)

Для ограничений назначения ниже нужен Xray-core 26.6.27 или новее на обоих узлах. Получите на каждом VPS одну и ту же проверенную рабочую копию Xrayebator с командами `profile-create --without-pq`, `private-cascade` и файлом `libexec/private_cascade_udp.py`. Установленный менеджер сам по себе не устанавливает этот отдельный обработчик и его unit-файлы. Выполняйте команды ниже из рабочей копии; если установленный менеджер старее, замените `sudo xrayebator` на `sudo bash ./xrayebator`. При обновлении используйте согласованные проверенные версии обработчика и сгенерированного конфига.

В свободном каталоге на каждом VPS получите проверенный тег или коммит, а не меняющийся latest-файл. До выполнения замените значение ссылки:

```bash
CASCADE_REVIEWED_REF='replace-with-reviewed-tag-or-commit'
git clone --no-checkout https://github.com/howdeploy/Xrayebator.git xrayebator-cascade-src
cd xrayebator-cascade-src
git fetch --depth 1 origin "$CASCADE_REVIEWED_REF"
git checkout --detach FETCH_HEAD
```

## Имена, сертификаты и REALITY

- Используйте уже имеющийся домен под вашим управлением. Выделите имена вроде `ingress.example.com` и `egress.example.com`. Направьте записи `A` на соответствующие публичные IPv4. Добавляйте `AAAA` после проверки доступности по IPv6 и ограничений firewall. Если DNS-провайдер предлагает проксирование, используйте режим DNS only. Служебное имя от хостинга подходит, если вы можете подтвердить необходимый контроль над DNS и выпускать и продлевать сертификат на это имя.
- Для стандартной маскировки REALITY оставьте рабочие SNI и TLS-цель, заданные в Xrayebator, и подключайтесь к VPS по IP. Для туннеля в этой схеме не требуется регистрировать домен или выпускать сертификат.
- Адрес для подключения каскада может быть доступным IP или именем. IP-сертификат подходит для HTTPS-подписки. Для self-steal задайте в SNI REALITY имя из сертификата TLS-сайта на loopback. Для XHTTP укажите это же имя в `host`. [Домен и DNS](configuration.md#домен-и-dns) · [Self-steal](configuration.md#собственный-домен-и-self-steal-заглушка)
- Для self-steal с закрытым портом 80 используйте ACME-плагин своего DNS-провайдера в режиме выпуска сертификата. Подключите сертификат к TLS-сайту на loopback, добавьте перечитывание конфигурации TLS-сервиса после продления и проверьте сертификат на loopback. Встроенная команда `dns01-setup` настраивает отдельный HTTPS-слушатель для подписки с Cloudflare или Route 53. Запускайте её, только если также хотите опубликовать подписку. Передавайте секрет через файл или stdin. [DNS-01](configuration.md#dns-01-сертификат-и-домен-подписки-без-порта-80)

## Подготовьте зарубежный узел

На зарубежном VPS создайте выделенный профиль legacy XHTTP командой `sudo xrayebator profile-create --name private-cascade-egress --transport xhttp --without-pq --port 25443`. Проверьте наличие имени в `names` и пустой список `errors`. Получите ссылку XHTTP в меню профилей и сохраните фактические значения `path`, `host` и `mode`. IPv6-адрес подключения возьмите в квадратные скобки.

```text
vless://<uuid>@<egress-address>:<port>?encryption=none&security=reality&type=xhttp&sni=<sni>&fp=<fingerprint>&pbk=<public-key>&sid=<short-id>&host=<host>&path=<url-encoded-path>&mode=<mode>
```

TCP Vision также поддерживается. Используйте `--transport tcp` без `--without-pq` на свободном порту, отличном от 443, и сохраните `flow=xtls-rprx-vision` в ссылке. При этом flow Xray отклоняет открытие UDP-сессий к порту 443 на зарубежном маршруте. Браузеры могут повторить HTTPS-запрос по TCP, если HTTP/3 недоступен. Пример с XHTTP поддерживает прикладной UDP/443.

Проверьте доступность порта с российского VPS и отказ с адреса вне списка разрешённых. Убедитесь, что зарубежный VPS может выходить в интернет. [Обычный каскад](configuration.md#каскад-и-upstream-ноды)

Зарубежный VPS самостоятельно разрешает имена назначения. Ограничьте его выход публичными IPv4-адресами, в том числе для каждого UDP-пакета. Сохраните защищённую копию конфига и добавьте следующий выход в `outbounds`. Два поля стратегии IPv4 обеспечивают совместимость с поддерживаемыми версиями ядра. Добавьте в список блокировки адреса метаданных хостинга, если их нет в наборе приватных адресов.

```json
{
  "tag": "private-cascade-exit",
  "protocol": "freedom",
  "settings": {
    "domainStrategy": "ForceIPv4",
    "finalRules": [{"action": "block", "ip": ["geoip:private", "::/0"]}]
  },
  "streamSettings": {"sockopt": {"domainStrategy": "ForceIPv4"}}
}
```

Эти ограничения относятся к назначениям клиентов. Межсерверное соединение может работать по IPv6.

В `routing.rules` зарубежного узла добавьте это правило после существующих правил блокировки и перед первым общим правилом, которое может принять трафик каскада, включая маршрут TCP/UDP по умолчанию. Если использовали другой порт или профиль, подставьте фактический тег входа вместо `inbound-25443`.

```json
{
  "type": "field",
  "inboundTag": ["inbound-25443"],
  "outboundTag": "private-cascade-exit"
}
```

Проверьте изменённый конфиг командой `sudo /usr/local/bin/xray run -test -config /usr/local/etc/xray/config.json`. После успешной проверки перезапустите Xray в окно обслуживания и подтвердите, что выделенный вход выбирает `private-cascade-exit`. При ошибке проверки или запуска восстановите и проверьте резервную копию перед возвратом службы. В одной XUDP-сессии отправьте первый пакет на контролируемый разрешённый IPv4-адрес, а второй — на контролируемый запрещённый адрес. Убедитесь, что первый дошёл, а второй был заблокирован. Проверьте ограничения и для IP, и для доменов, которые разрешаются в эти адреса.


## Подготовьте списки маршрутизации

Пример ниже использует установленный `geosite.dat` для российских категорий и компактные списки Re-filter для заблокированных доменов и адресов. Перед обновлением существующих файлов сохраните их хеши и защищённые копии. Скачайте оба набора из одного релиза и проверьте SHA-256 из метаданных GitHub перед установкой. [Источники Re-filter](https://github.com/1andrevich/Re-filter-lists)

```bash
(
  set -eu
  stage=$(mktemp -d)
  trap 'rm -rf -- "$stage"' EXIT
  curl -fsSL https://api.github.com/repos/1andrevich/Re-filter-lists/releases/latest \
    -o "$stage/release.json"
  for kind in geoip geosite; do
    name="$kind.dat"
    url=$(jq -er --arg name "$name" '.assets[] | select(.name == $name) | .browser_download_url' "$stage/release.json")
    hash=$(jq -er --arg name "$name" '.assets[] | select(.name == $name) | .digest | select(test("^sha256:[a-f0-9]{64}$")) | ltrimstr("sha256:")' "$stage/release.json")
    curl -fsSL "$url" -o "$stage/$name"
    printf '%s  %s\n' "$hash" "$stage/$name" | sha256sum -c -
  done
  sudo install -o root -g xray -m 0644 "$stage/geoip.dat" /usr/local/share/xray/refilter-geoip.dat
  sudo install -o root -g xray -m 0644 "$stage/geosite.dat" /usr/local/share/xray/refilter-geosite.dat
)
```

Сохраните установленную базу стран с категориями `geoip:private` и `geoip:ru`. Политика использует `geosite:available-only-in-ru` и `geosite:category-ru` из установленной базы доменов. Если этих категорий нет, обновите или выберите проверенные данные перед генерацией. После изменения списков проверяйте новый конфиг. При неудачном обновлении восстановите прежние файлы перед перезапуском действующего каскада.

## Сгенерируйте конфигурацию и запустите входной узел

На российском VPS выберите рабочий инбаунд VLESS REALITY TCP или legacy XHTTP с `decryption=none` и пустым списком VLESS `fallbacks`. На чистой установке выделите свободный порт для шаблона и оставьте его закрытым в firewall провайдера. Выполните `sudo xrayebator profile-create --name private-cascade-template --transport xhttp --without-pq --port 15442`. Проверьте наличие имени в `names` и пустой список `errors`. В основном конфиге появится `inbound-15442`. Отдельная служба будет слушать свой порт, в этом примере `15443`.

Сгенерируйте новый UUID для выделенного входа командой `uuidgen`. В каталоге, доступном только root, например `/root/xrayebator-private-cascade/`, создайте два файла владельца root с правами `0600`. Запишите одну ссылку зарубежного узла в `upstream.txt`. Заполните `policy.json` по примеру, заменив тег инбаунда, UUID и демонстрационные адреса назначения своими значениями.

```json
{
  "inbound_tag": "inbound-15442",
  "client_id": "<cascade-client-uuid>",
  "listen": "0.0.0.0",
  "port": 15443,
  "udp_relay_port": 15444,
  "udp_dispatch_port": 15445,
  "russia_only_domains": ["geosite:available-only-in-ru"],
  "blocked_domains": ["ext:refilter-geosite.dat:refilter"],
  "blocked_ips": ["ext:refilter-geoip.dat:refilter"],
  "russian_domains": ["domain:ru", "domain:su", "domain:xn--p1ai", "geosite:category-ru"],
  "russian_ips": ["geoip:ru"]
}
```

Выберите свободный TCP-порт и откройте его для нужных клиентов в firewall хоста и провайдера. Массивы `blocked_domains` и `blocked_ips` обязательны. Хотя бы один из них должен содержать правило. Необязательные массивы `russia_only_domains`, `russian_domains` и `russian_ips` определяют прямые маршруты. Для двух последних значения по умолчанию покрывают `.ru`/`.рф` и `geoip:ru`. Указывайте селекторы Xray, доступные в установленных базах. Для `ext:` нужны соответствующие локальные файлы данных. Генератор использует базы на VPS без загрузки из сети.

Чтобы отключить необязательный список, укажите пустой массив. Если поле пропущено, генератор использует значение по умолчанию.

Значения `udp_relay_port` и `udp_dispatch_port` по умолчанию — `15444` и `15445`. Выделите для них два свободных непривилегированных TCP-порта на российском VPS. Все три порта должны различаться. Локальные порты слушают только `127.0.0.1`; не открывайте их в firewall хоста или провайдера. Генератор записывает отдельный пароль обработчика и UUID классификатора в защищённый конфиг. Не передавайте эти внутренние данные клиентам.

Входной узел блокирует приватные и IPv6-адреса назначения, которые совпадают с его правилами по IP. Sniffing сохраняет переданный клиентом адрес из этих запрещённых наборов. Для остальных TCP-соединений распознанное имя становится фактическим назначением. Домен из `russia_only_domains` имеет приоритет перед списками блокировок и при передаче имени, и при передаче его публичного IP с тем же SNI. Списки блокировок имеют приоритет перед общими российскими правилами. Прямые выходы разрешают имена только в IPv4 и повторно проверяют адрес назначения при подключении. Маршрут по `russian_ips` разрешает соединения только с адресами из этого списка. Если результат повторного DNS-запроса противоречит выбранному прямому маршруту, соединение закрывается.

Для UDP публичный инбаунд сначала передаёт каждый пакет локальному обработчику с аутентификацией, включая запросы к виртуальному DNS и запрещённым адресам. XUDP может менять назначение внутри одной сессии. Поэтому обработчик открывает отдельный VLESS UDP-поток с неизменным назначением для каждого адреса и порта этой сессии. Затем Xray применяет к нему перехват DNS, запреты адресов и пять правил в нужном порядке. Обработчик не дублирует доменные/IP-списки и сам не подключается к интернет-ресурсам. Его локальное обрамление Trojan не меняет клиентский VLESS REALITY и не требует нового домена или сертификата.

Распознанный российский UDP может выходить напрямую из России. При отказе зарубежного узла зарубежные TCP и UDP останавливаются без прямого обхода; российские TCP/UDP и DNS входного узла продолжают работать. При отказе обработчика прикладной UDP, в том числе виртуальный UDP DNS, останавливается, а TCP сохраняет свои маршруты. Обработчик отклоняет полезную нагрузку больше 8190 байт, а не дробит её; буферы обрамления Xray размером 8 КиБ могут дополнительно уменьшать доступный размер в зависимости от адреса и заголовка. Приложения с крупными датаграммами проверяйте отдельно. Фиксированные ограничения числа соединений, потоков, очередей и времени бездействия ограничивают ресурсы обработчика; при их достижении соответствующий трафик отбрасывается или закрывается без выбора другого выхода.

Ключ разделения — адрес назначения и порт внутри исходной ассоциации. Сниффинг выполняется в начале такого потока с фиксированной целью; разные QUIC-соединения к одному адресу и порту не классифицируются заново по каждому SNI. Это маршрутизация назначений, а не проверка каждого сообщения приложения.

Входной узел использует служебный DoH с локальным резолвером в резерве. Настройте клиентский DNS на `192.0.2.53:53` внутри VLESS. Виртуальный адрес выделен для DNS на порту 53. Отключите на клиенте автоматическое переключение на прямое подключение или другой профиль.

```bash
sudo xrayebator private-cascade render \
  --policy-file /root/xrayebator-private-cascade/policy.json \
  --upstream-file /root/xrayebator-private-cascade/upstream.txt \
  --output /root/xrayebator-private-cascade/ingress.json
```

Если установленный менеджер ещё не содержит генератор, запустите `sudo bash ./xrayebator private-cascade render` с теми же аргументами из проверенной рабочей копии проекта.

Генератор добавляет публичного клиента с новым UUID и берёт его flow из первого клиента исходного инбаунда. Также он создаёт внутренний loopback-классификатор и данные доступа обработчика. Параметры публичного транспорта и REALITY сохраняются. Генератор проверяет конфигурацию через `xray run -test` и записывает новый файл владельца root с правами `0600`. Это проверка конфига Xray, а не доступности службы обработчика. Для первой установки выберите отдельный свободный каталог.

```bash
sudo install -d -o root -g xray -m 0750 /etc/xray-private-cascade
sudo install -o root -g xray -m 0640 /root/xrayebator-private-cascade/ingress.json \
  /etc/xray-private-cascade/config.json
sudo install -d -o root -g root -m 0755 /usr/local/libexec
sudo install -o root -g root -m 0755 libexec/private_cascade_udp.py \
  /usr/local/libexec/xrayebator-private-udp.py
command -v python3
```

Команда установки берёт обработчик из проверенной рабочей копии, а не отдельно загруженный latest-файл. До запуска убедитесь, что Python 3 установлен по пути `/usr/bin/python3`; на поддерживаемых Debian/Ubuntu при его отсутствии установите пакет `python3`. Конфиг должен принадлежать root и читаться только группой `xray` (`0640`): он нужен обеим службам.

Создайте от root файл `/etc/systemd/system/xray-private-cascade-udp.service`:

```ini
[Unit]
Description=Xray private cascade UDP destination splitter
PartOf=xray-private-cascade.service

[Service]
User=xray
Group=xray
NoNewPrivileges=true
ExecStart=/usr/bin/python3 /usr/local/libexec/xrayebator-private-udp.py --config /etc/xray-private-cascade/config.json
Restart=on-failure
```

Создайте от root файл `/etc/systemd/system/xray-private-cascade.service`. `Wants` запускает обработчик и сохраняет TCP-маршруты при его отказе. `PartOf` останавливает или перезапускает обработчик вместе со входным узлом. Право привязки к низкому порту позволяет использовать свободный порт 443. Оба локальных порта обработчика оставьте выше 1023. Пример использует стандартные пути Xrayebator к бинарнику и базам.

```ini
[Unit]
Description=Xray private cascade ingress
Wants=network-online.target xray-private-cascade-udp.service
After=network-online.target xray-private-cascade-udp.service

[Service]
User=xray
Group=xray
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
Environment=XRAY_LOCATION_ASSET=/usr/local/share/xray
ExecStart=/usr/local/bin/xray run -config /etc/xray-private-cascade/config.json
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl start xray-private-cascade.service
sudo systemctl status --no-pager xray-private-cascade.service xray-private-cascade-udp.service
ss -ltn 'sport = :15443'
ss -ltn 'sport = :15444 or sport = :15445'
```

Убедитесь, что оба локальных слушателя используют `127.0.0.1`. Работающая служба Xray сама по себе не подтверждает UDP. При обновлении сохраните защищённые копии конфига, обработчика и обоих unit-файлов. Проверьте кандидат и перезапустите входной узел, чтобы обработчик через `PartOf` перечитал согласованные данные доступа. При неудачной проверке или приёмке восстановите эти файлы вместе.

Возьмите ссылку первого клиента из исходного инбаунда за образец в закрытом канале. Подставьте новый UUID, адрес и порт отдельной службы. Сохраните параметры REALITY, flow, fingerprint и настройки транспорта, в том числе `host`, `path` и `mode` для XHTTP. Импортируйте ссылку как отдельный тестовый профиль. При ротации обновите UUID в отдельном конфиге и выдайте новую ссылку.

## Обновление и удаление

Отдельный каскад обслуживается вручную. Перед обновлением сохраните защищенные копии конфига, установленного помощника и обоих unit-файлов. Переключите исходники на проверенную ревизию, сгенерируйте и проверьте новый конфиг с новым путем вывода, затем установите его и повторно скопируйте `libexec/private_cascade_udp.py` в `/usr/local/libexec/xrayebator-private-udp.py`. Сверьте оба unit-файла с инструкцией и внесите изменения. После изменения unit-файлов выполните `sudo systemctl daemon-reload`, затем перезапустите `xray-private-cascade.service`, чтобы помощник перечитал те же учетные данные. Повторите приемку и при ошибке восстановите сохраненные файлы вместе.

Перед запуском общего `uninstall.sh` выполните откат ниже. Сначала остановите входной узел и помощник, затем удалите `/etc/systemd/system/xray-private-cascade.service`, `/etc/systemd/system/xray-private-cascade-udp.service`, `/etc/xray-private-cascade/` и установленного помощника. Выполните `systemctl daemon-reload`, закройте публичные порты каскада и удалите его зарубежный профиль и выделенное правило маршрутизации. Сохраняйте защищенные исходные файлы и резервные копии, пока они нужны для отката. При использовании обычных установщика, обновления и удаления оператор обслуживает эти отдельные файлы и службы вручную.

## Проверьте каскад и подготовьте откат

1. С компьютера или клиента командной строки в нужной сети проверьте подключение REALITY и выполните несколько небольших HTTPS- и DNS-запросов. По журналам на контролируемых ресурсах подтвердите, что явно выбранный российский маршрут выходит с российского адреса, а маршрут по умолчанию — с зарубежного. Проверьте домен из российского исключения, чей публичный IPv4 также входит в `blocked_ips`, по имени и по IP с тем же SNI. Оба запроса должны доходить до фактического российского исключения напрямую. Обычный российский домен с адресом из списка блокировки должен идти через зарубежный узел.
2. В одной настоящей XUDP-сессии отправьте небольшие UDP-пакеты на контролируемый российский, зарубежный и заблокированный адрес, затем снова на российский. Подтвердите исходящий адрес каждой доставки и ответы; повторите в обратном порядке и с запросом к виртуальному DNS в начале. Заблокированное назначение должно идти за рубеж, даже если его адрес российский. Приватные и IPv6-назначения не должны получать пакеты. Раздельные тесты с одним назначением такую смену не проверяют.
3. В окно обслуживания отключите только выделенный зарубежный канал и откройте новые тестовые соединения. Прямые российские TCP/UDP и виртуальный DNS должны работать, зарубежные TCP/UDP — остановиться без трафика с российского выхода. Восстановите канал и проверьте связь. Отдельно остановите только `xray-private-cascade-udp.service`: прикладной UDP и виртуальный UDP DNS должны остановиться без обхода, а TCP — сохранить маршруты. Запустите обработчик и проверьте восстановление.
4. Сверьте обычную службу Xray, профили, подписки, Hysteria 2 и AmneziaWG с исходным состоянием. Отдельные службы сохраняют их маршруты и настройки. После успешной проверки включите запуск при загрузке только входного узла командой `sudo systemctl enable xray-private-cascade.service`; его `Wants` запускает обработчик.
5. Для отката отключите профиль каскада на клиенте и выполните `sudo systemctl disable --now xray-private-cascade.service`, затем `sudo systemctl stop xray-private-cascade-udp.service`. Убедитесь, что все три слушателя на входном узле исчезли. Удалите два выделенных unit-файла и установленный конфиг; удаляйте установленный обработчик, только если его использует исключительно этот каскад. Выполните `sudo systemctl daemon-reload`. Закройте только выделенные публичные порты в обоих firewall: для loopback-портов публичные правила не нужны. Удалите профиль зарубежного узла командой `sudo xrayebator profile-delete --name private-cascade-egress`, затем его правило маршрутизации и выход `private-cascade-exit`. Если создавался профиль `private-cascade-template`, удалите его по имени на российском VPS. Повторно проверьте исходные службы.
