## Сервисный аккаунт и права

Xray работает от системного пользователя `xray`. Drop-in
`/etc/systemd/system/xray.service.d/security.conf` задаёт `User=xray` и сужает capabilities до
`CAP_NET_BIND_SERVICE` — этого достаточно для низких портов. Состояние менеджера намеренно находится
вне границы записи сервисного аккаунта.

Модель прав:

| Путь или класс | Владелец и доступ |
|---|---|
| `/usr/local/etc/xray/` и его каталоги состояния | В основном root-owned и не записываются сервисом; сгенерированные metadata вроде `.server_country` могут принадлежать `xray` |
| `config.json`, профили и маркеры миграций | Обычно `root:root`, читаемы Xray; rollback может дать live config `root:xray` и `0640` |
| Приватные ключи Reality и VLESS | `root:root`, режим `0600` |
| Публичные ключи и сгенерированные метаданные | Читаемы там, где нужны сервису или handler'у подписки; ownership metadata может отличаться |
| `/usr/local/etc/xray/scripts/` и `/usr/local/bin/xrayebator*` | `root:root`, исполняются только как root-скрипты |
| `/var/log/xray/` | записывается runtime-аккаунтом Xray для журналов сервиса |

Сервисный аккаунт читает нужную конфигурацию, но не может заменить профили, маркеры, root-скрипты
или приватные ключи. Бэкапы принадлежат root и лежат отдельно от live-файлов. Отдельные
сгенерированные метаданные (например, `.server_country`) могут быть созданы helper-путём, а live-конфиг
при rollback-пути может получить `root:xray`; проверяйте конкретные файлы при аудите. Не храните
посторонние секреты в каталоге состояния Xray.

Runtime-изменения, выполняемые `xrayebator`, используют backup, валидированную атомарную запись и
транзакцию `safe_restart_xray`. Установщик и project updater — отдельные lifecycle-программы: у них
свои шаги валидации и контролируемого рестарта/rollback, поэтому некорректно говорить, что каждый
lifecycle-путь вызывает `safe_restart_xray`.

## Безопасность подписки

URL подписки — bearer-credential. Он не публичен, но любой, кто получил полный URL, может скачать
список маршрутов и защищённые токеном ресурсы подписки.

Что уже сделано на стороне сервера:

- токен 32 hex-символа, генерируется `openssl rand -hex 16`;
- `/sub/` без валидного токена возвращает одинаковый `404`;
- профиль без живых маршрутов возвращает `410` и не выдаёт маршруты;
- nginx добавляет `Cache-Control: no-store` и rate-limit на location подписки;
- корень `/` и пути вне `/sub/` возвращают `404`;
- `Revoke` меняет `sub_token`, старый URL перестаёт работать.

Что остаётся на операторе:

- не публиковать `subscription_url` в открытых чатах или трекерах;
- при утечке сразу нажать `Revoke`;
- относиться к каждой сохранённой ссылке `vless://` как к credential;
- не отдавать внешнему клиенту local-only URL;
- не держать на том же домене чужие панели и прокси, не разобравшись в конфиге nginx.

## Доступ к VPS по SSH

Установить Xrayebator можно прямо из-под `root`, но лучше отдельный пользователь с узко ограниченным sudo.

На сервере:

```bash
adduser <username>
usermod -aG sudo <username>
su - <username>
```

На своём компьютере:

```bash
ssh-keygen -t ed25519 -C <your_email@example.com>
ssh-copy-id <username>@<айпи_сервера>
```

Затем зайдите как `<username>@<айпи_сервера>`. Если вход по ключу работает, отключите пароль и при
желании запретите root-login:

```bash
sudo nano /etc/ssh/sshd_config
```

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

> Потеряете SSH-ключи — потеряете доступ к серверу. Сначала убедитесь, что вход по ключу работает, и
> только потом отключайте пароль.

Чтобы SSH не рвался во время настройки VPN, полезен keep-alive:

```text
ClientAliveInterval 60
ClientAliveCountMax 120
TCPKeepAlive yes
```

## Пароли в десктоп-GUI

Активный Electron-GUI поддерживает SSH по паролю и приватному ключу, с прямым root или sudo. Выбранный через нативный dialog приватный ключ main process сохраняет через `keytar` в системное хранилище ОС (Windows Credential Manager, macOS Keychain или Linux Secret Service). Поэтому ключ можно повторно использовать для SSH-операций и после перезапуска приложения. Renderer получает только несекретный credential id и отображаемое имя файла; байты приватного ключа не переходят через preload boundary.

Если системный keychain недоступен, plaintext-фолбека на диске нет: ключ остаётся только в памяти main process до выхода из приложения, а GUI предупреждает, что после перезапуска ключ придётся выбрать снова. SSH-пароль сохраняется в системный keychain только после первого успешного входа и далее переиспользуется; отдельный sudo-пароль и passphrase зашифрованного ключа не сохраняются и вводятся заново при необходимости.

`electron-store` сохраняет карточку сервера и настройки подключения, credential id и имя ключа, диагностику установки, `subscription_url`, полученные `vless://`-ссылки и SHA-256 pin SSH host key. URL подписки и VLESS-ссылки — bearer-credentials: защищайте локальные данные Electron-приложения и отзывайте подписку при утечке. При удалении последней карточки, ссылающейся на credential, соответствующая запись keychain удаляется; общая запись остаётся, пока на неё ссылается другая карточка.

Импорт по SSH распознаёт только установку Xrayebator и по умолчанию выполняет read-only диагностику; частично настроенный сервер сохраняется с честными статусами без автоматического исправления. Email при развёртывании можно не указывать: тогда Certbot использует `--register-unsafely-without-email`, поэтому уведомления о продлении и восстановление ACME-аккаунта будут недоступны. GUI предупреждает об этом до запуска.

SSH host key работает по TOFU после первой успешной аутентификации. Fingerprint затем закрепляется; при последующем несовпадении подключение останавливается до выполнения команд. После осознанной переустановки VPS явно сбросьте pin в Server Settings и подтвердите новый ключ при следующем успешном подключении.

См. [Electron Desktop GUI](desktop-gui.md) для полной границы Electron, карты команд и деталей сборки.
